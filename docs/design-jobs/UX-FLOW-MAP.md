# UX Flow Map

The founder's format, one line per chain:

```
MODULE → SCREEN → ACTION → NEXT STATE → CONNECTED MODULE → RESULT
```

**319 chains, synthesised from 285 findings across nine UX-audit lanes**
(`findings/UX-A.jsonl` … `UX-I.jsonl`). Grouped by the module that owns the
SCREEN. Inside each group the chains that do not hold are listed **first** and
marked, because a chain that fires and reaches nobody is what this map exists to
make visible.

This is the **experience** map. Its sibling `MODULE-INTERACTION-MAP.md` is the
**data** map (151 chains, entity → event → listener). Where a chain appears in
both, the `MOD-*` id is cited on the row. Neither supersedes the other: that map
answers "does the event reach a listener", this one answers "does the screen keep
its promise".

---

## How to read a row

- **NEXT STATE** is what the product actually does next, not what the button says.
- **RESULT** is what the USER loses or gets, stated so a designer can decide what
  to draw. "No listener" is a fact about a program; "the canvas keeps showing the
  draft value until an unrelated edit or a reload" is the same fact, usable.
- Every non-working row carries its finding id and a `file:line`. Rows with no
  citation are working chains traced to a lane's module-summary row, which lists
  the files read.

### The three failure kinds — they are not the same problem

| Mark | Meaning | Redesign consequence |
|---|---|---|
| **BROKEN** | The step runs and does the wrong thing, or reports a result it did not produce. | Fix the code before drawing anything. A screen cannot be designed around a lie. |
| **MISSING** | The step does nothing, or the control does not exist at all. | A screen has to be designed. Nothing to preserve. |
| **UNDISCOVERABLE** | The step works correctly and has no door, or a door nobody finds. | Pure IA work. Do not rebuild the feature. |

A fourth mark, **DUPLICATE**, is used where two surfaces do the same job with
different rules — the user's result depends on which door they found. These are
IA decisions, not bugs, but they produce bug-shaped complaints.

## Contradictions, corrections and closures

Findings are evidence, not gospel. Where two lanes disagree, both ids are named
here rather than one being picked silently.

**1. Is Publish (and History) on the rail?**
`UX-E-01` and `UX-E-31` label the Publish panel "rail · U"; `UX-I-42` calls
History a "rail tab". `UX-F-01` and `UX-F-37` say neither is on the rail — the
rail renders exactly six ids. Both readings are literally true at different
levels and the map uses the second: `tabsConfig.ts:349-351` `RAIL_FIGMA =
[add, layers, pages, assets, content, design]`; Publish and History are
*registered tabs with shortcuts* (`U`, `H`) that render **no rail button**. Read
"rail · U" in lane E as "shortcut U".

**2. Is bare `D` bound?**
`UX-C-25` says the palette prints `D` for "Open Content panel" and that bare D is
bound nowhere. `UX-F-05` and `UX-F-31` say twelve panels are bound to bare
letters including D. **Re-verified in this lane: D IS bound** —
`useSidebarKeyboard.ts:34-47` iterates `GROUPED_TABS_CONFIG` and matches
`tab.shortcut === key`, so the literal search for `key === "d"` in UX-C-25 was a
false negative. But UX-C-25's *observable* claim survives for a different reason:
`LeftSidebar.tsx:486` passes `safeTabChange`, which per `UX-F-02` changes the
active tab **without opening the drawer** — so with the drawer closed, pressing D
does re-target the rail and shows nothing. The badge is honest; the handler is
half-wired. Both rows are kept, re-pointed at the real cause.

**3. Do CMS bindings survive a reload?**
`MODULE-INTERACTION-MAP.md` marks `MOD-A-03` **STALE — do not act on it** on the
strength of the founder's uncommitted `Composer.ts` work. `UX-C-01` re-tested it
and says that blanket is itself wrong: the fix round-trips in the **standalone**
editor and is inert for **real sites**, because `editorSaveProjectSchema`
(`packages/shared/schemas/sites.ts:192-214`) has no `.passthrough()` and
`BuildrikSyncProvider.ts:293-338` never re-reads `cmsBindings`. The map's own
"correction to that correction" agrees. Treat MOD-A-03 as **half-stale**: fixed
for the demo, live for every customer.

**4. The Layers breakpoint badge — found twice, one chain.**
`UX-D-19` (Inspector lane) and `UX-H-16` (Layers lane) are the same defect
reached from opposite ends: `useLayerTree.ts:88-95` never populates
`breakpointOverrides`, so the T/M badges at `LayerTreeItem.tsx:276-281` can never
render. One chain, two ids, no disagreement.

**5. Three different truths about "locked".**
`UX-D-02` (inspector renders every control enabled for a locked element),
`UX-H-15` (Layers selects locked elements the canvas refuses) and `UX-H-14` (the
padlock is read from `localStorage`, the enforcement from the element model, and
they never reconcile) are three halves of one broken concept. Not contradictory;
cumulative, and worse together than any one of them reads alone.

**6. Corrections to earlier passes, carried here so they are not re-filed.**
- `W-J-12` claimed five Insert tips exist in code; `UX-A-14` counted **four** at
  this HEAD (`catalog/tips.ts:11-28`).
- The prior "dynamic pages screen is unwired" claim is **stale** — `UX-B-25`
  re-verified that the view is spelled `dynamic-pages` and does render.
- `D-F-38` claimed `ai.summarize` has no editor caller. It has one
  (`useAISummary.ts:109`). Already refuted at `VERDICTS.jsonl:199`, still being
  carried in `DESIGN-AUDIT-SUMMARY.md:99`.
- The brief's framing that CMS detail pages ship the template's canonical/og:url
  is wrong; `UX-E-31` verified the server injects a correct per-path pair. What
  IS the template's is the first `<title>`, og:title, og:description and
  twitter:* (`UX-E-05`).
- `UX-H-23` **closes** a previously-filed defect: the 40px eye/lock controls in
  28px Layers rows are fixed (`layers-v2.css:157-168`). What remains is a 20×20
  target under the 24×24 minimum.
