### L1-001 Click-to-insert puts blocks INSIDE the selected heading or text
- Module / Screen-location / Feature: Add panel → click-insert; smart placement
- Labels: BROKEN FUNCTIONALITY, CODE ONLY ISSUE
- Category: Broken existing feature
- Type: Functional
- Severity: High
- Problem: when a Heading or Text element is selected, clicking any element in the Add panel (Divider, Image, …) inserts it as a child of that text element.
- Expected behavior: a text-level element is never a drop container for blocks. The new element goes after the selected element, as a sibling.
- Current behavior:
  - LIVE: with a Heading selected, Add → Divider produced `<h2>Heading<hr></h2>`. The inspector breadcrumb read "Home › Heading › Divider".
  - LIVE: with a Text inside a Section selected, Add → Image produced `<p>Lorem…<img></p>`. The breadcrumb read "Home › Section › Text › Image" (`11-inserts`, `12-state.png`).
  - Layers shows the same wrong nesting.
  - A double-click on the heading afterwards deep-selects the Divider instead of editing the heading text (`22-inline-heading.png`).
- Figma status: not checked
- Code status:
  - `editor/shell/hooks/useBlockInsertion.ts:97` uses the non-strict `canNestElement`.
  - In `shared/utils/nesting/rules.ts:200-235`, `heading` has `allowChildren: true` and BLOCK category children. Its `forbiddenChildren` omits divider, image, container, spacer and video. `paragraph` forbids container but not image or divider.
  - `canNestElementStrict` exists (`validator.ts:112`) but is not used here.
- Integration impact: the bad nesting is saved and persists after reload. It is what triggers L1-002, where text is lost on export and publish.
- Probable root cause: the nesting rules let text elements accept block children; placement only asks `canNestElement`.
- Dependencies: L1-002
- Recommended next action:
  - Make text types (heading, paragraph, label, link) leaf containers for anything except inline phrasing, or use `canNestElementStrict` in placement.
  - Add a test: heading selected + insert Divider → sibling.
  - Add a migration or repair step for documents that already contain such nesting.
- Evidence: LIVE-VERIFIED

### L1-002 Export and publish drop an element's own text once it has a child
- Module / Screen-location / Feature: Export / Publish serializer (cross-module: canvas → export → publish)
- Labels: BROKEN FUNCTIONALITY, INTEGRATION ISSUE, CODE ONLY ISSUE
- Category: Broken existing feature
- Type: Integration
- Severity: Critical
- Problem: the canvas renders both an element's text and its children. The exporter writes children OR text, never both. A heading that contains a child (L1-001) is published without its words.
- Expected behavior: export matches the canvas. Text and children are both serialized, or the editor never creates this state.
- Current behavior: LIVE, Export site → Code shows:
  - `<h2 …><hr …></h2>`: the word "Heading" is gone.
  - `<p …><img alt="Image"></p>`: the paragraph text "Lorem ipsum…" is gone.
  - The Export preview shows neither (`k-Meta_Shift_e.png`, `sm-Export_site.png`).
  - The in-editor Preview (⌘P) still shows them (`k-Meta_p.png`). Preview and the live site therefore disagree.
- Figma status: no board (serializer)
- Code status:
  - `engine/export/ExportEngine.ts:486-494`: `else if (children.length > 0) {…} else if (content) {…}`.
  - The same pattern is at `:1242`.
  - The publish path uses the same engine (`editor/shell/exportPublishPages.ts:45-46`, `ExportEngine.exportAllPages`).
- Integration impact: silent content loss on the customer's published site. No pre-publish check catches it.
- Probable root cause: the serializer assumes content and children are mutually exclusive, but the editor model allows both.
- Dependencies: L1-001 is the common trigger. Pasted HTML, AI output or legacy content could also produce it.
- Recommended next action:
  - Decide the model invariant: either an element with text cannot have element children (enforce in the engine), or serialize both, in order.
  - Add an export test for heading text + child.
  - Add a pre-publish check for "element text will be dropped".
- Evidence: LIVE-VERIFIED (export output). The publish path is CODE-ONLY because no real publish was allowed.
