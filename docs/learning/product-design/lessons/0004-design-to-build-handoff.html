Lesson 4 · ~7 minutes

Design one thing. Then tell the builder exactly what to build.

You asked the right workflow question: "can we design each thing, then build it — and what do I tell the coder?" Yes. That's how professionals work: decide the design, write a tight handoff, build it, move to the next surface. The skill that's easy to skip is the handoff — turning a decision into an instruction a builder can execute without guessing.

A build instruction has four parts
1. WHAT (the design) · 2. WHERE (which file) · 3. DON'T-BREAK (the rules) · 4. DONE (how you'll know)

Why each part exists

PartWhat it answersIf you skip it…
WHATThe exact layout / behaviour you decidedThe builder invents its own design — back to "AI-designed"
WHEREThe file / component to changeHours lost hunting, or the wrong thing gets edited
DON'T-BREAKThe project's rules + what must keep workingIt builds, but violates the design system or breaks a feature
DONEHow you'll both agree it's finishedEndless "is it right yet?" with no answer

The skip that hurts most: DON'T-BREAK

The first three are obvious; the fourth is what separates a spec from a wish. Your "vibcoder" isn't a generic coder — it's your codebase's component library + its rules. So "build it with vibcoder" really means: use the existing buttons, keep the one accent colour, don't touch the engine, keep the keyboard shortcuts wired. Naming those up front is what stops a build that "works" but quietly breaks the system.

Today's topbar handoff, in one breath: WHAT three zones + a ⋯ overflow, Publish as the only blue button · WHERE Topbar.tsx, keep every existing handler · DON'T-BREAK vibcoder buttons only, cobalt only, engine untouched, shortcuts kept · DONE three groups visible, tsc clean, tests green. Full version: docs/reviews/audit-mockups/topbar-build-spec.md — written to be pasted straight to a build session.

The loop, in order

  1. Inventory — list everything currently on the surface (the topbar had ~16 controls; the list is the density problem, made visible).
  2. Decide — apply one rule to keep / move / hide each item (you did this: Publish stays loud, breadcrumb leaves, rare things go to ⋯).
  3. Handoff — write the 4-part spec.
  4. Build — one surface, then verify against DONE.
  5. Next surface — repeat. Never redesign everything at once.
