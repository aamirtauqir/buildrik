"100% right" isn't a feeling. It's a ladder you climb.

You can never prove software is perfect — you build confidence in layers. Each rung catches a different kind of mistake. Climb them in order; only the top rung counts as done. The golden rule that makes all of this safe: a UI redesign re-lays-out, it never re-wires. Move the boxes, keep the wires — then verify the wires still carry current.

1
Types — npx tsc --noEmit
Catches broken wiring shapes: a button calling a handler that doesn't exist, a prop of the wrong type. If it compiles, the connections at least fit.
Confidence: the wires are plugged into the right shaped sockets.
2
Tests — npx vitest run [the touched area]
The existing tests describe how the thing should behave. If they still pass after your change, you didn't break the behaviour they cover.
Confidence: known behaviours still hold.
3
Walk every state — in the real app
Open it and reproduce each state from the states checklist: empty, loading, error, and the app states (here: Saved → Saving → Offline → Reconnecting → Publishing → Published → Failed). Each must look right.
Confidence: it's complete, not just the happy path.
4
Click every action — does it actually do the thing?
Press Undo → did the canvas undo? Click Publish → did it really publish? This proves the wires carry current — that re-laying-out didn't quietly disconnect a handler.
Confidence: the logic still fires from the new layout.
5
Acceptance — tick the spec's DONE list
Every build spec ends with a DONE section (the four-part handoff). Read it line by line against the result. All ticked → done. Any unticked → not done, no matter how good it looks.
Confidence: it matches what we agreed to build.

The one rule that prevents most breakage

Presentation ≠ logic. A good UI component is "dumb": it receives state + callbacks as props and only renders + calls them. The real logic lives outside it. So a redesign that touches only layout and style — never which handler a button calls or where its data comes from — cannot break business logic, because it never touches the logic. Verify it didn't anyway (rung 4), but by construction it shouldn't.

So, "is it 100% right?"

Answer honestly: "all five rungs pass." That's the most truthful "yes" software allows. Skipping rungs is how a change that looks done ships a broken Publish button. Climb all five, every time.
