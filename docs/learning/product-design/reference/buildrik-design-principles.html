Reference · Buildrik Design Constitution · v1

The principles every editor decision follows.

This is the small set of rules that turn "design" from taste into a system. Any control, any panel, any new feature gets decided by running it against these — not by what looks nice. Hand this to any builder ("vibcoder"): same rules, every surface, = a coherent editor. When two of us disagree, we don't argue taste — we cite the principle.

Words & honesty

1 Match the real world

Use the user's words, never the code's.

"Heading", not "h2". "Text", not "Typography / div". Labels are written for a client, not an engineer.

Test: would a non-technical client understand this word?

2 One status, one truth

Two parts of the UI must never disagree about the same fact.

The topbar can't say "Save failed" while the footer says "Offline". One source, one message.

Test: does any other part of the screen contradict this?

3 Don't promote what isn't ready

A broken or demo-only feature never gets prime space.

Real-time collab is demo-only → design the presence slot, but gate it until it's solid.

Test: would I be happy if a client used this exactly as shown today?

Hierarchy — what's loud, what's quiet

4 Prominence = frequency × importance

Loud = used often AND matters. Quiet or hidden = rarely both.

Agency name (never changes) left the breadcrumb; the page name (changes often) got bold.

Test: score it — how often × how much. Low on both → tuck it away.

5 The loudest button is the product's purpose

Exactly one primary (filled, cobalt) button per surface — and it names why the tool exists.

A website builder exists to publish → Publish is the hero, not Ask AI.

Test: finish "this tool exists so the user can ___" — that's the hero.

6 Calm by default — content is the hero

The thing the user is making (the canvas) is the most prominent; chrome stays quiet until needed.

No blueprint outlines at rest; selection chrome appears only on the selected element.

Test: at rest, does the eye land on the work or on the toolbar?

Restraint — the discipline that prevents clutter

7 Earns its way in — default no

Prime space (the topbar) rejects by default. A control must pass: ready? · global? · always-needed?

Invite, ⌘K, Help, Account all failed "always-needed" → they live in the ⋯ overflow.

Test: all three yes? In. Any no? Panel or overflow.

8 Subtract before you add

When tempted to add, first ask what can move out.

16 scattered topbar controls → 3 zones + ⋯. The fix for density is fewer things, not tidier things.

Test: what did I remove to make room for this?

9 Tuck the rare — progressive disclosure

Show the common; hide the rare one click deep (⋯, "More", a dropdown).

Advanced inspector controls collapse under "More settings"; Client-view folds into Preview ▾.

Test: do most users need this most of the time? No → tuck it.

Consistency — the same, everywhere

10 Group by intent

Things that share a job sit together, separated from other jobs by a divider or a label.

Topbar = Navigate │ View │ Status+Ship. Rail = Make the page / Make it yours.

Test: can I name the job each group does in one word?

11 One canonical name per thing

A thing has exactly one name, used on every surface.

A heading is "Heading" in the toolbar, breadcrumb, and inspector — never four different names.

Test: does this thing have a different label anywhere else?

12 One shared skeleton

Every panel uses the same frame: Header → (optional) nav → grouped body. Only the content differs.

Insert, Pages, Styles, Settings should feel like one family, not four apps. This is the cure for "it feels AI-designed."

Test: could I swap this panel's header/padding for another panel's and notice no difference? Good.

Completeness — a design isn't one picture

13 Design every state, not just the happy one

A surface is a SET of states — default, hover, focus, loading, empty, success, error, disabled, plus app states (offline, saving, publishing, collab-on). It's not done until each is designed.

The topbar isn't finished at "Saved" — it also needs Saving… · Offline · Reconnecting · Publishing… · Published · Failed. See the states checklist.

Test: have I designed empty · loading · error · the edge (too-long / too-many)? If not, it's not done.

Structure — where everything lives

14 Every feature has one home

Each feature is reachable from exactly one place, grouped by the user's job — not by the backend module that built it. The two surfaces split by scope: Editor = inside one site; Dashboard = across sites / the business.

"Site settings" lived in three places (editor tab · dashboard · settings hub) → picked one. The feature list was grouped by PRD module (the system's shape) → regroup by the six user jobs. This is the whole-product big brother of #10 "Group by intent".

Test: can a user reach this from two places? And does its group name a user job, or a backend module?

15 Lock the spine; dock additions to the edge

The core layout — rail slots, topbar zones, the one hero button, the inspector frame — holds a fixed position across every version. A new feature never reorders the spine; it docks into an existing home (a panel, a sub-tab, the ⋯ overflow).

➕ Insert stays rail-slot #1 forever; a new element type goes inside the Insert panel, not as a new rail icon. The user's muscle memory survives every release. (Visible promise = spatial stability / consistency; the "why" = pace layering — fast features must not move the slow core.)

Test: did adding this move anything the user already knew the position of? If yes — redock it to the edge.

16 Tools live near the work

A control's distance from the thing it acts on is set by how often it's used. Frequent canvas operations — undo/redo, edit history, breakpoint switch, zoom — hug the canvas (a canvas toolbar). The topbar carries only rare, global actions: publish, share, exit, account. Reaching across the screen for a frequent action is a tax.

Undo/redo + breakpoints + history left the topbar for a canvas toolbar; the topbar slimmed to Exit · Share · Publish · ⋯ — every survivor infrequent or global. Frequency decides not just how loud a control is (#4) but where it lives. Grounding: Fitts's Law (distance to target = effort) + the "tools near work" pattern in Figma/Framer.

Test: how often is this used, and what does it act on? Frequent + acts-on-canvas → put it by the canvas. Rare + global → topbar / ⋯.

How to use this

Designing any surface? Run the five-step loop — inventory → decide (cite a principle for each call) → 4-part handoff → build → next — and let these rules settle every decision. A "complete" surface is one designed in all its states (#13), not just at rest. Disagreement is resolved by pointing at a number, not by opinion.

Principles vs patterns. Keep this list small and general. Situation-specific rules ("how we do an empty state", "how we confirm a delete") are patterns, which live a level below and grow freely. The hierarchy: Principles (few, general — this page) → Patterns (recurring solutions) → Components (real buttons/cards) → Tokens (colour/spacing/type). New situations usually add a pattern, not a principle. Principles are sharpened, added, or retired only rarely — but always written here first, so the whole editor moves together.

This constitution distils the course lessons (1–5, plus later additions through L20 = principle #16) into one page. Grounding source: NN/g 10 Usability Heuristics. Inspiration for "design principles as a constitution": designsystems.com.

Think a principle is wrong, or missing? Tell me — we revise the constitution together. That's how a design language stays alive.
