PROTOTYPE
Save / autosave lifecycle (§8) · grounded in current autosave (BuildrikSyncProvider → tRPC) · solution: autosave is silent on the happy path, loud only when something's at risk
Topbar indicator — click to step states
…editor topbar…Saved
✓ Saved exists
Steady state. Quiet — no spinner, no nag. Timestamp on hover ("saved 12s ago").
↻ Saving…
Debounced after edits. Brief, non-blocking — you keep editing.
⚠ Offline — changes queued SOLUTION
Network dropped. Edits buffer locally; banner reassures "saved on this device, will sync when back". Never silently lose work.
↺ Reconnecting → flushing queue
Auto-retry on reconnect; queued edits flush in order. Resolves to Saved.
✕ Save failed
Server rejected (rare). Explicit "Retry" + "Download a backup" — work is recoverable, not a dead-end. Distinct from offline (this is a real error).
Principle: the indicator earns attention only when work is at risk. Happy path = nearly invisible (Tesler's Law — the system carries the saving burden, not the user).
