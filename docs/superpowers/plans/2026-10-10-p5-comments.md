# P5 · Comments — Manage, Threads, Mentions, Apply with AI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Comments can be edited and deleted by their authors and moderated by admins, with visible attribution (L5-033). They gain one level of replies under a root comment or pin, and a deleted root becomes a placeholder that keeps its replies (L5-031). They then gain permission-aware @mentions that notify without ever granting access (L5-032). Last, a located comment can be handed to AI as a reviewable proposal and resolved after acceptance (L5-027).

**Architecture:** Each phase follows Page → tRPC → Router → Service → Prisma, extending `server/services/comment.service.ts` and `server/trpc/routers/comments.ts` for team members and `client-review.service.ts` / `routers/client-review.ts` for token-authenticated client reviewers. Storage changes come in **two additive, owner-applied migrations**: (A) edit/delete/thread columns together, so the Review state model is migrated once, and (B) a mention table. The editor surfaces live in `chrome-ui/CommentRow.tsx` (rows), `sidebar/tabs/review/ReviewTab.tsx` (panel) and `canvas/comments/CommentLayer.tsx` (pins). Notifications use the existing `notification.trigger.ts` `createNotification`, which already applies in-app preferences.

**Tech Stack:** Prisma 5 / PostgreSQL, tRPC 11, Zod, Vitest (mocked Prisma, plus the `*.db.test.ts` tier for constraints), React 18 editor chrome (chrome-ui, `tw:`, `--bk-*`), Next.js dashboard (`/review/[token]`).

## Global Constraints

- **Phase order is binding:** Tasks 1–4 (L5-033) merge before Tasks 5–8 (L5-031). Mentions (Tasks 9–11) start only after replies **and** the reply notification (Task 8) are live. Apply with AI (Tasks 12–13) starts after replies, and after `2026-10-10-p5-ai-actions.md` Task 4 (`AiProposalCard`) and Task 1 (site-scoped `streamPrompt`).
- Permissions are enforced on the **server**. UI hiding is a convenience only. The role ranks are in `lib/constants/enums.ts:66`: VIEWER 0, EDITOR/DESIGNER 1, ADMIN 2, OWNER 3. Site role comes from `getEffectiveSiteRole` (`permission.service.ts:162`).
  - Authors may edit or delete their own comment at any role that can see the site.
  - ADMIN and above may edit or delete anyone's comment.
  - Client reviewers act only on comments carrying their own `reviewerId`, through the token.
- **Mentioning never grants access.** A mention of a user without site access is stored as plain text, sends no notification and creates no row.
- Services throw `CommentError` (extend its code union). Routers translate it: NOT_FOUND → NOT_FOUND, FORBIDDEN → FORBIDDEN, BAD_REQUEST → BAD_REQUEST, GONE → NOT_FOUND with reason "deleted".
- Shared Zod lives in `packages/shared/schemas/comments.ts`. No `../../`. Chrome uses `@/editor/chrome-ui`, with no raw native controls (Gate 24).
- **Migrations are owner-applied.** Agents write the SQL and run `prisma generate` only.
- Every UI task follows the FIGMA loop (`packages/editor/CLAUDE.md`). Review v2 is the authority: section `8165:219385`, START HERE `8167:227951`, comment-sent `8167:227374`, comment-reopened `8170:223872`, changes-requested `8165:220437`. Boards for edit, delete, reply and mention do not exist yet (Task 0 brief).
- Live steps never publish from the QA workspace. Sending a review round in a local dev workspace is fine.

## Review Focus

1. **Two people edit the same comment, or an admin deletes a root while its author is typing a reply.** Expected: the stale write is refused with "This comment changed — reload to see the latest" (`expectedUpdatedAt` precondition, the same pattern as the CMS `updateMany` precondition). The reply to a deleted root is still accepted and lands under the placeholder. Pinned in Tasks 2 and 6.
2. **A client reviewer's link expires or is revoked between loading the page and editing their comment.** Expected: the edit is refused with the page's existing expired-link state. There is no partial write. Pinned in Task 4.
3. **The last reply under a deleted root is deleted.** Expected: the placeholder disappears as well. Resolved and open counts are unchanged by placeholders, which never count as open. Pinned in Task 6.
4. **@-mentioning someone who lost site access after the picker loaded.** Expected: the server stores plain "@Name", sends no notification, and the composer shows nothing that implies they were told. Pinned in Task 10.
5. **"Apply with AI" on a comment whose element moved or was deleted since the comment was made, or whose page is not open.** Expected: the action is disabled with "This comment isn't attached to an element on this page" (located comments only). It never runs against a guessed target. Pinned in Task 12.

## Reality check (code is truth; `origin/main` @ `503bc62cd`)

1. **The Comment model has no edit, delete or thread fields** (`prisma/schema.prisma:498-524`). Its columns are `id, siteId, pageId?, authorId?, reviewerId?, body, x?, y?, targetSelector?, status (OPEN|RESOLVED), resolvedById?, resolvedAt?, createdAt, updatedAt`. A SQL CHECK requires exactly one of authorId and reviewerId (`20260720120000_client_review_loop`). `authorId` has **no relation** to `User`. The owner said "confirm storage needs before promising no migration": the storage **is** needed (Task 0 records why), so there is a migration.
2. **Comments are linked to the site, not to a review round.** The Review v2 state model (FG-001/004, not built) reasons about rounds, but comments carry no round id. The owner wants the thread migration coordinated with the Review state model. Migration A therefore adds only thread, edit and delete columns and leaves round/snapshot linkage to the FG-006 pins plan (its own migration). Task 0 maps every comment state to a Review v2 board state.
3. **The router has `create`, `list`, `workspaceList`, `reattach` and `resolve`** (`server/trpc/routers/comments.ts:40-110`, all `protectedProcedure`). `create` uses `assertSiteAccess`, so VIEWERs can post, with a rate limit of 30/min. `resolve` and `reattach` require EDITOR. `CommentError` has code `NOT_FOUND` only (`comment.service.ts:12`).
4. **Internal authors render as "You"** (`ReviewTab.tsx:689`), because `listComments` never resolves internal author names, only `reviewer.name` and `resolvedByName`. Attribution for moderation needs names, so Task 2 resolves them.
5. **`ReviewService.postReply` (`packages/editor/src/services/ReviewService.ts:283`) is not a reply.** It is an unpinned `comments.create`, and the composer is labelled "team only" (`ReviewTab.tsx:1117`). Task 7 renames it to `postSiteComment` so the name stops lying, and adds a real `postReply`.
6. **Client reviewers see only their own comments** (`listClientComments`, `client-review.service.ts:313`, filtered by `reviewerId`). Team replies on a client thread are therefore invisible to the client unless the list query changes (Q2).
7. **Notifications have no comment, reply or mention types** (`lib/constants/enums.ts:149-170`). The "Feedback" category exists (`:192-193`). `createNotification` (`notification.trigger.ts:23`) applies the in-app preference. **Email delivery is not wired for any type** (`emailSent` is read nowhere), so "respects notification prefs" means the in-app preference only (Q3).
8. **L5-030 is fixed** (`416ce8e61`): team comments show without a round (`ReviewTab.tsx:860`).
9. **AI.** `streamPrompt` (`server/trpc/routers/ai.ts:334`) takes no `siteId` and does no site permission check. Quota is per user (`quota.service.ts:75`). `set-text` refuses markup (`applySetStyle.ts:145-154`). Both are addressed in the AI-actions plan, which Task 12 depends on.
10. **Anchors** are `[data-buildrick-id="…"]` only (`canvas/comments/commentAnchors.ts:23`), with orphan detection and reattach. "Located comment" = `targetSelector` resolves via `resolveAnchor` on its `pageId`.
