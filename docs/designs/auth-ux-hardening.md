### 10x Check
Email-first unified flow + progressive auth: users see the product before they're asked
for a password. Type your email, see a workspace template, sign up only when you click "Save."
Reduce time-to-value from 4 steps to 1.

### Platonic Ideal
You open the app. There's one field: your email. You type it. If you have an account, a
magic link appears in your inbox and you click it. If you don't, you're in a workspace in
15 seconds with your work waiting for you. Password is optional, surfaced after you're
already invested. OAuth is shown once, prominently. 2FA is a security add-on, not a speed
bump. You never see an error message that reads like a database field name.

## Implementation Approach

Approach B: Auth UX Hardening. Fix all user-visible conversion holes in one pass.
Reuses existing create-session API, generateToken, handleAuthError.
No new patterns, no routing changes. Estimated ~220 LOC including tests (~120 LOC implementation, ~100 LOC tests). Per-item LOC estimates in the scope table are implementation-only and do not include tests.

### create-session API Contract
`POST /api/auth/create-session` — route at `app/api/auth/create-session/route.ts`
- **Request body:** `{ sessionToken: string, rememberMe?: boolean }` (rememberMe already supported — no route change needed)
- **Success:** `200 OK`, body `{ success: true }` — NextAuth cookie is set
- **Errors:** `400` (invalid input), `401` (invalid token), `403` (CSRF), `404` (user not found)
- **`createClientSession` behavior:** See "createClientSession error contract" in Key Design Decisions — all error handling is in one place there.
- **Redirect responsibility:** `createClientSession` only makes the fetch and returns a boolean. The **caller** is responsible for calling `router.push("/auth/redirect")` after receiving `true`. `createClientSession` never navigates.

### Inbox Shortcuts — "Open your email app" fallback
For unrecognized domains: render plain text "Open your email app" with no link. Do not use a `mailto:` link (it opens the user's default email client, which may not be the one the verification email went to). Plain text + "Check your inbox" copy is sufficient.

### Shared Helper
Extract `createClientSession(sessionToken: string, rememberMe?: boolean): Promise<boolean>`
to `lib/auth/create-session.ts`. Used by login, 2FA, backup, and verify-email pages.
Returns `false` on any failure — never throws. See "create-session is a raw fetch" in Key Design Decisions for the full error contract.

### Key Design Decisions (resolved)
- **verifyEmail returns sessionToken (router mints it, not the service):** Service refactored to return `{ user: User, tokenType: "email_verify" | "email_change" }` (currently returns `user` only — this is a new return shape). Router calls `generateToken("session_grant", user.id, SESSION_GRANT_TTL_MINUTES)` ONLY when `tokenType === "email_verify"`. The service does not generate the token. This prevents auto-login on email-change confirmations. Only `verify-email/page.tsx` calls `trpc.auth.verifyEmail` — no other callers, no regression risk from the response shape change. **Edge case:** if `generateToken` throws after email is already verified and token invalidated, the router must catch this and return `{ success: true, user, sessionToken: null }` — NOT re-throw. This ensures `onSuccess` fires on the frontend and the page shows the graceful fallback ("Email verified! Please sign in.") instead of an error screen.
- **`session_grant` is an existing token type** defined in `server/services/token.service.ts`. Already used in `server/trpc/routers/auth.ts` (lines 46, 115, 128, 140). `generateToken` is imported from `@/server/services/token.service`. No new types or schema changes needed.
- **session_grant token TTL is 5 minutes:** Short enough to limit replay window (email links stay in inboxes). Long enough for users on slow connections or mobile email apps. Named constant `SESSION_GRANT_TTL_MINUTES = 5` in the router (same value already used for other session_grant calls in the file).
- **rememberMe transport:** sessionStorage key `buildrik_rememberMe`. Read-once: call `sessionStorage.removeItem` immediately after reading, before calling `createClientSession`. Private browsing fallback: try/catch on the `sessionStorage.getItem` call only — defaults false. The try/catch does NOT wrap `createClientSession`. Access sessionStorage inside `useEffect` (not at render time and not with `typeof window !== "undefined"` — that pattern causes hydration mismatches in React 18+). Note: React Strict Mode mounts components twice in development — the read-once `removeItem` means the second mount reads null and defaults `rememberMe` to false. This is expected behavior in dev (Strict Mode only); production mounts once.
- **create-session is a raw fetch, not tRPC:** Intentional deviation from CLAUDE.md "pages call tRPC" rule. The route handler (`app/api/auth/create-session/route.ts`) sets httpOnly cookies — this cannot be routed through tRPC. The deviation is limited to `lib/auth/create-session.ts`. The route handler already accepts `rememberMe` — no backend change needed.
- **`createClientSession` error contract:** Returns `false` on any failure (network error, any non-200 status, thrown exception). Never throws. Callers do NOT use try/catch — branch on the boolean result and show a context-appropriate fallback message. This is the single authoritative spec — the API Contract section describes the HTTP layer; this decision covers the helper's behavior.
- **"Sign in instead" pre-fills email via `?email=`:** `login/page.tsx` is a `'use client'` component — read the search param via the `useSearchParams()` hook (from `next/navigation`), not from server props. Use `const searchParams = useSearchParams()` and initialize email state as `useState(searchParams.get("email") ?? "")`. The CTA link must use `encodeURIComponent(email)` — email addresses with `+` signs (common Gmail aliases) will be misread otherwise.
- **2FA "resend" is NOT a resend:** TOTP codes come from the authenticator app. The fake "Resend (45s)" text is replaced with a recovery code link. No new endpoint needed.
- **Auto-login fallback:** If create-session fails after verification, show "Email verified! Please sign in." Never leave the user stuck.

The only change is wrapping the return value.

## Data Flow: Auto-Login After Verification

```
User clicks email link
  |
  v
verify-email/page.tsx (token in URL)  ← CLIENT COMPONENT (must be 'use client')
  |
  v
trpc.auth.verifyEmail.mutate({ token })
  |
  v
auth.ts router: verifyEmail → service validates token
  → returns { user, tokenType }
  |
  if tokenType === "email_verify":
    router calls generateToken("session_grant", user.id, SESSION_GRANT_TTL_MINUTES)
    returns { ..., sessionToken }
  if tokenType === "email_change":
    returns { ..., sessionToken: null }
  // if token is invalid/expired → service throws AuthError("TOKEN_EXPIRED", ..., 410)
  //   → handleAuthError re-throws as tRPC error → onError fires → show existing error message
  |
  v
Page: if (sessionToken) → createClientSession(sessionToken)
       // DO NOT call createClientSession(null) — guard is required
       if (!sessionToken) OR createClientSession returns false:
         → show "Email verified! Please sign in." with link to /auth/login
  |
  v
Redirect to /auth/redirect → app
  (/auth/redirect is an EXISTING route — app/auth/redirect/page.tsx uses useOnboardingFlow()
   to dispatch: new users → onboarding steps, returning users → dashboard. Correct target
   for both first-signup auto-login and returning-user 2FA. No callbackUrl needed.)
```

## Data Flow: 2FA rememberMe Passthrough

Both `2fa/page.tsx` and `2fa/backup/page.tsx` use identical rememberMe logic.
The backup page calls `verifyBackupCode` instead of `verify2FA`, but the
session creation step is the same — read rememberMe, call createClientSession.

Both pages MUST be `'use client'` — sessionStorage is not available on the server.
Access sessionStorage inside `useEffect` only (see Key Design Decisions for why
`typeof window !== "undefined"` is banned — causes hydration mismatches).

```
login/page.tsx  (client component)
  |
  requiresTwoFactor = true
  |
  if (rememberMe === true):
    try { sessionStorage.setItem("buildrik_rememberMe", "true") }
    catch { /* private browsing — ignore */ }
  // if rememberMe === false: do NOT write the key (read side defaults to false on missing key)
  |
  v
router.push("/auth/2fa?token=...")  ← rememberMe NOT in URL (privacy)
  |
  v
2fa/page.tsx OR 2fa/backup/page.tsx  (client components):
  let rememberMe = false
  try {
    rememberMe = sessionStorage.getItem("buildrik_rememberMe") === "true"
    sessionStorage.removeItem("buildrik_rememberMe")  ← read-once
  } catch { /* private browsing → default false */ }
  |
  v
verify2FA (or verifyBackupCode) success
  → createClientSession(sessionToken, rememberMe)
```
