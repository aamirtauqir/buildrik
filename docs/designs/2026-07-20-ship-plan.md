## 1. The finding this plan is built around

The wedge is one argument away from working.

```ts
// packages/editor/src/services/ReviewService.ts:20
export async function submitForReview(note?: string, changeSummary?: string) {
  await client.reviews.submit.mutate({ siteId, note, changeSummary });
  //                                                              ^
  //                                            clientEmail is never passed
}
```

Everything downstream of that call already works:

- `submitReviewInput` **accepts** `clientEmail` (`packages/shared/schemas/reviews.ts`)
- `submitReview` **mints a token** when it gets one (`review.service.ts:57`)
- and **sends the client the invite email** (`review.service.ts:61 → :155`)
- `/review/<token>` **renders, identifies, comments and approves** — walked
  against the real database, wrong-email rejected, `authorId` null with
  `reviewerId` set, `resolvedById` null on approval

So today the editor's **Send for review** submits to the *internal admin queue*
and never invites anybody. The product's entire reason for existing is gated on a
parameter that is already typed, already validated, and already handled.

That is not a small thing dressed up as a big one. It means **the first
milestone below is days, not weeks** — and it changes what to do first.

## 2. Sequence

### M1 · Make one real review reachable — *first, and alone*

Nothing else matters until an agency can send a link and a client can sign it.

1. **Pass `clientEmail` through.** `submitForReview` takes it; the S5.1 compose
   state is already drawn (`S5.1 · compose`), including the four states the send
   itself needs — `sending`, `sent`, and the one that matters: `error`, where the
   email fails but **the link still works and is copyable**, because the link
   exists whether or not the mail lands.
2. **Decide the `agency_layer` flag.** `reviews.submit` is gated on it
   (`reviews.ts:32`). Client review is deliberately *not* gated
   (`client-review.ts` header) — a link that was legitimately issued must keep
   working even if a workspace flag flips. Turn the flag on for the pilot
   workspace, or lift the gate.
3. **Wire the review-status pill.** Six states drawn (`S5.2 · *`). The one worth
   building first is `opened-not-acted` — "she hasn't opened it" and "she opened
   it and said nothing" are different conversations, and only one of them is the
   designer's problem.

**Done when:** a designer in a real workspace sends a link, a real client opens
it on their own machine, and the approval lands in the database with their name
on it.

### ╞═ GATE C — the only gate left ═══════════════════════════

**Put `S5.5` in front of a real agency's client.** Not the agency — their client.
The wedge runs on the person who has never heard of us.

Three questions, and only three:

1. Opening the link, **without being told** — can they say what this is and what
   is being asked of them?
2. Name and email before commenting — **necessary, or a wall?**
3. Pressing Approve — **do they know what they just agreed to?** The page shows a
   snapshot frozen at send. If they think they approved "the website" rather than
   "this version", the frozen-snapshot decision (contracts §1.6) has not landed
   and the copy needs to change before anything else is built on it.

Everything after this point assumes the answers were yes. If they were not, stop
and fix the copy — it is the cheapest thing in this document to change and the
most expensive to get wrong.

### M2 · Make the review page show the site

The preview is honestly a placeholder today, and it says so on screen rather than
faking it. Filling it in is the largest single piece of engineering left.

- `SiteVersion.payload` already persists the frozen `ProjectData` (schema:1048).
- Turning that into HTML lives in the editor's `ExportEngine`, which has **not**
  been proven to run inside Next. That is the actual unknown; budget for it
  failing and needing a server-side path.
- ⚠ **Do not shortcut this by embedding the live draft.** It is easy, it looks
  right, and it silently breaks the frozen-snapshot contract — the client reviews
  work that has already moved on, which is the exact dispute the product sells
  itself as preventing.
- Open question, engineering's to settle: contracts §3.1 calls the approved side
  *full page HTML*; §3.3 says the stored snapshot is *ProjectData JSON* through
  the same renderer. Different artifacts, different fidelity. **Pick one and
  write it down** — Compare and the review page both depend on the answer.

### M3 · Close the permission gaps the design already assumes

Both are decided and neither is built:

- **`sites.publish` is `ADMIN`-gated** (`sites.ts:276`) while the locked decision
  is that a **DESIGNER may publish**. The design draws the enabled case
  (`Permissions · Publish`, marked Allowed). Until the code changes, the drawing
  and the product disagree.
- **The rest of the matrix** (contracts §2) is drawn as disabled-with-reason —
  approve, rollback, domains, brand push, shared-library edit, site delete. The
  design's rule is that a denial is **shown with its reason, never hidden**,
  because a designer who cannot see the control cannot learn the rule and files a
  bug instead.

### M4 · Migrate the editor accent in code

Design is `#406ED6`; `packages/editor/src/themes/design-system/color.css:33` is
still cobalt `#2D6DFF`. Until this lands, the running editor will not match the
file — which is fine and documented, but it is a real cost every time someone
compares them and has to remember why.

Own token contract, own CI gates, so it is its own piece of work rather than a
find-and-replace.

### M5 · The rest of the editor

Everything else in the design file. This is the largest bucket by volume and the
least urgent by risk — it is assembly against drawings that already exist and
states that have already been enumerated. Nothing here is blocked on a decision.

## 4. How this plan is most likely to go wrong

Not a risk register. Three specific failure modes this project has already
demonstrated, written down so they are recognisable the next time.

**Building M5 before M1.** M5 is the biggest, most visible, most satisfying pile
of work and it is blocked on nothing. It is also worth nothing until a client can
sign something. The order above is deliberate and the temptation is real.

**Trusting a checklist over the specs.** This file's own build checklist reached
"complete" three separate times while requirements it had no row for sat
undone — 12 shell states, then 80 more, then J5's 31. A checklist only ever
audits itself. Read the specs and check them against what exists, never the
reverse.

**A search that assumes a format.** J5's 31 states and Domains' 6 stayed
invisible through a sweep that matched `**States:**` while those files write plain
`States:`. The result was a confident, verified, *wrong* report of 171/171. When
sweeping for something, grep the loosest form and read what does not match.

## 5. What "done" means

The wedge is shipped when an agency, without being helped:

1. finishes a client site in the editor,
2. sends it for review to their client's real email address,
3. the client opens it, understands it, comments on it and approves it,
4. the designer publishes it,
5. and, six weeks later, both sides can still see **who approved what, and when**.

Step 5 is the one that makes it a wedge rather than a feature. Everything else
Webflow already does.
