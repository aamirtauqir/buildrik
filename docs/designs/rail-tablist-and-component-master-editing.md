## Problem Statement

Two decisions surfaced by the 2026-08-20/21 editor walk, both verified live, both
deliberately left unfixed because each one changes structure rather than a line.

**1. The rail's tab semantics are invalid.** `LeftSidebar` renders
`<nav role="tablist">` with `role="tab"` buttons and a `role="tabpanel"` drawer.
axe reports **aria-required-children (critical)** whenever a drawer is open:
"Element has children which are not allowed: `div[aria-describedby]`,
`[role=tooltip]`". Each rail button is wrapped in a flowbite `Tooltip`, which puts
two extra elements inside the tablist. A tablist may own only tabs, so the whole
tab set stops being announced as one.

**2. Components can be created but never edited.** The component library offers
Insert, Duplicate, Delete, Detach and Variants. Nothing changes a component after
it exists. `ComponentManager.updateComponentMaster` and `syncAllInstances` are
built, tested, and called by nothing outside their own tests.

## What This Unlocks

The rail is the most-used chrome in the product; making its roles true means a
keyboard or screen-reader user gets "tab 3 of 7, panel attached" instead of seven
unrelated buttons. And a component you can edit is the difference between a
library and a clipboard: change the button once, forty instances follow.

## Evidence

Rail:
- axe, with a drawer open: `aria-required-children`, critical, on `nav.ls-rail`.
  Clean at rest, which is why every earlier sweep missed it.
- flowbite-react 0.12.17 `TooltipProps` = `{ animation, arrow, content, placement,
  style, trigger }` plus `ComponentProps<"div">`. No portal, container, or target
  option.
- `Floating.js` renders a **Fragment**: `<div className={theme.target}>` (trigger
  wrapper) and the `role="tooltip"` bubble as **siblings**. Arbitrary props spread
  onto the bubble, not the wrapper — so neither child can be re-roled from the
  outside.
- Tried and reverted 2026-08-21: `role="presentation"` on `.ls-zone` plus
  `aria-hidden` on the logo/divider/spacer. The violation persisted — a
  presentational wrapper is transparent, so the tooltips surfaced to the tablist
  directly.
- `@floating-ui/react@0.27.17` and `@floating-ui/dom` are already in the lockfile
  (transitive via flowbite). `chrome-ui` already exports `OverlayMount`,
  `OverlayRoot`, `getOverlayRoot` and `Portal`, which Gate 22 names as the legal
  portal primitives.
- 12 files use `<Tooltip`. The rail accounts for two of them (`RailZone`,
  `FigmaRail` in `LeftSidebar.tsx`).

Components:
- `updateComponentMaster(id, elementId)`: deep-clones `element.toJSON()` into
  `masterTree`, bumps `version`, persists, emits `COMPONENT_UPDATED`, then calls
  `syncAllInstances` when `autoSyncInstances` is set — and its default is `true`
  (`DEFAULT_COMPONENT_CONFIG`, `shared/types/components.ts:270`).
- `syncInstance` re-clones the master, re-applies each instance's stored overrides
  through `applyOverridesToTree`, and counts the ones whose target element no
  longer exists — reporting them only through `devError`, which is a no-op in
  production.
- Callers outside tests: zero, for `updateComponentMaster`, `syncInstance`,
  `resetInstance` and `detachAllInstances`.
- Walked live: create → instantiate → detach → delete all work; delete survives a
  reload; editing the element a component was made from does **not** reach the
  instance (master 3px, instance unset), which is correct for the API and useless
  for the user.
- The 2026-04-17 design `components-variant-management` already assumed master
  edits happen ("when masterTree changes — user edits source element") and already
  set the orphan-override policy: dropped, with a recommendation to re-add. That
  design was approved at 10/10 scope and its variant work still depends on this.

## Constraints

- Editor chrome: `chrome-ui` + flowbite-react + `tw:` utilities + generated
  `--bk-*` tokens. No new CSS bundle; the styling ratchet counts CSS lines and
  hoisted inline styles.
- Gate 22: `createPortal` / `document.body` only through `OverlayMount`,
  `OverlayRoot`, `Portal`, `Toast`, or the allowlist.
- `gate:chrome-ui-surface` locks the **flowbite wrapper** set at exactly two
  (`TextInput`, `Select`). A tooltip that does not wrap flowbite's Tooltip is an
  editor-specific component like `Modal` or `Toast` — 47 of those already live in
  `chrome-ui` — so the closed set is untouched.
- Gate 24: no raw `<button>/<input>/<select>/<textarea>` outside `chrome-ui`.
- `AquibraStudio.tsx` is the founder's file: never staged from an agent session.
- Board fidelity: the rail tooltip (label + shortcut) is drawn; it has to survive.

## Premises

1. The rail is structurally invalid as a tablist while tooltips render inside it.
2. Any real fix is structural: stop being a tablist, stop rendering tooltips
   inside it, or stop having rail tooltips.
3. It is not cosmetic — an invalid tablist costs AT users the tab-set
   relationship, not just a lint line.
4. Component editing has no door onto an engine that is already built and tested.
5. Without that door, changing a component means delete, recreate, re-place.
6. Whichever affordance ships, overrides pointing at removed master elements get
   dropped, and the UI has to say so out loud.

Founder confirmed all six and asked for both to be fixed.

## Approaches Considered

### Decision 1 — rail semantics

**A. Wrapper-free portal tooltip in chrome-ui (CHOSEN).** A tooltip that clones its
single child instead of wrapping it, attaches ref and handlers to that child, and
renders the bubble through the overlay root. The tablist's children become exactly
the `role="tab"` buttons. Effort human ~1 day / CC ~2-4h.

**B. Rail becomes navigation.** Drop tab/tablist/tabpanel, use `aria-current` and a
labelled region. Rejected: cheapest and honest, but it trades the tab-set
relationship away permanently to work around a component's markup.

**C. Drop rail tooltips.** Rejected: regresses a boarded detail on the most-used
chrome to save a component.

### Decision 2 — component editing

**A. "Update component from selection" now, edit mode later (CHOSEN).** One action
that promotes the selected element's tree to the master and lets the existing sync
fan it out, behind a confirm that names the cost. Effort human ~half a day /
CC ~1-2h.

**B. Component edit mode.** Isolate the master on canvas, edit, exit to a change
summary. Not rejected — deferred. It is the destination, and the April variant
design assumes it; it is not the first step.

**C. Push changes from an instance.** Rejected as the entry point: the same edit
meaning "this one" or "all of them", decided after the fact, is where users
misfire — though the mechanic is the same engine call as A.

## Recommended Approach

### 1. `chrome-ui/HintTooltip` — the portal tooltip

- API: `<HintTooltip content={ReactNode} placement="bottom-end" delay={150}>{child}</HintTooltip>`.
  Exactly one element child; cloned with `ref`, `aria-describedby`, and pointer /
  focus handlers. No wrapper element in the DOM.
- Bubble: rendered through `Portal` / `OverlayMount` into the overlay root with
  `role="tooltip"` and a generated id. Positioned with `@floating-ui/react`
  (already in the lockfile — promote it to a direct dependency of
  `packages/editor` rather than leaning on a transitive).
- Behaviour to preserve from the current rail tooltips: label plus shortcut text,
  `placement="bottom"`/`"bottom-end"`, no arrow, `max-w-[280px]`, normal
  whitespace. Focus shows it immediately, hover after the delay, Escape and blur
  dismiss it.
- Migrate the rail only (`RailZone`, `FigmaRail`). The other ten `<Tooltip>` sites
  stay on flowbite until someone has a reason to move them.
- Verify: axe with **each** drawer open (the state that fails today), keyboard Tab
  through the rail with the tooltip showing, and a screenshot against board
  `199:2` so the visual is unchanged.

### 2. "Update component" — the door onto the engine

- Action in `ComponentDetailScreen`'s Component Actions row, beside Duplicate.
  Enabled when the canvas selection is non-empty; disabled with a reason when it
  is not.
- Confirm before it runs (`ConfirmDialog`, destructive tone): name the component,
  the number of instances that will change, and that overrides pointing at removed
  elements will be lost.
- Make the loss visible: `syncInstance` currently counts dropped overrides and
  only `devError`s them. Return the count up through `syncAllInstances` and
  `updateComponentMaster`, and toast "N override(s) couldn't be re-applied" when
  it is non-zero. This is the smallest change that turns premise 6 into behaviour.
- Not Pro-gated. Detach sits behind the design-system density toggle; editing a
  component is not an advanced flourish.
- Tests: engine (version bump, sync fan-out, override re-application, orphan
  count) and UI (disabled with no selection, confirm gate, toast on drop).
- Live walk before it counts as done: create a component, place two instances,
  override one, edit the source element, press Update — both instances follow, the
  surviving override survives, and a deliberately orphaned override is reported
  rather than silently dropped.

## Open Questions

- Does `HintTooltip` replace flowbite's Tooltip everywhere eventually, or stay the
  variant used inside role-constrained containers? Decide after the rail ships and
  the component has real mileage.
- Touch behaviour for the rail tooltip: long-press, or accept that a shortcut hint
  is a pointer/keyboard affordance? The editor is desktop-only per DESIGN.md, so
  the honest default is to skip touch.
- Should "Update component" also be reachable from the canvas context menu on an
  instance? Cheap to add later; not needed to open the door.

## Success Criteria

- axe reports zero violations on the rail with every drawer open, and the rail
  still exposes `role="tablist"` with seven `role="tab"` children and the drawer
  as its `tabpanel`.
- The rail tooltip still renders label plus shortcut, matching board `199:2`.
- A component edited through Update propagates to every instance in one action,
  with instance overrides preserved where their targets still exist and reported
  where they do not.
- `updateComponentMaster` and `syncAllInstances` have production callers — the
  dead-export scan for the components engine returns nothing.
