Option A vs Option B — Full Comparison

Editor-Dashboard Integration Approaches

Option A — Embed Editor Inside Next.js

Single app, single deploy, editor lives at /dashboard/sites/[siteId]/editor

Advantages

  • Single deploy — ek hi Vercel/server pe sab kuch
  • Shared auth — NextAuth session directly available, koi extra setup nahi
  • tRPC direct access — editor mein tRPC hooks seedha use ho sakte hain
  • No CORS issues — same origin, koi cross-domain masla nahi
  • Seamless UX — user ko tab switch nahi karna, same app mein rehta hai
  • Shared components — dashboard ke UI components (modals, toasts, sidebar) reuse
  • Single routing — ek hi router, deep linking easy
  • Simpler DevOps — ek build pipeline, ek CI/CD

Disadvantages

  • Build complexity — Emotion CSS (editor) + Tailwind 4 (dashboard) ek saath configure karna
  • SSR conflicts — Editor purely client-side hai, Next.js SSR se conflict hoga (dynamic import + ssr:false lagega)
  • Bundle size — Editor ka poora code dashboard bundle mein aayega (~2MB+), initial load slow
  • Migration effort — Vite-specific features (import.meta, env vars) ko Next.js compatible banana
  • Tight coupling — editor update = dashboard redeploy, dono tied hain
  • Dev experience — Turbopack + Emotion HMR issues possible
  • Risk — Editor ke 371+ components mein koi bhi break ho sakta hai migration mein
  • Timeline — Estimated 3-6 weeks sirf build integration ka kaam

Option B — Separate Apps, API Bridge

Editor stays Vite app, connects to dashboard via API, same domain pe deploy

Advantages

  • Zero editor rewrite — editor jaise hai waise kaam karta rehta hai
  • Fast to ship — sirf API bridge banana hai, 1-2 weeks
  • Independent deploys — editor fix = editor deploy, dashboard untouched
  • StorageAdapter ready — editor mein already "remote" mode hai with custom handlers
  • Performance — editor ka bundle alag load hota hai, dashboard fast rehta hai
  • Team independence — editor aur dashboard teams alag kaam kar sakti hain
  • Low risk — existing code mein minimal changes
  • Rollback easy — kuch break ho toh sirf ek app rollback

Disadvantages

  • Auth sharing setup — session cookie sharing chahiye (same domain pe solve hota hai)
  • Two deploys — dashboard.buildrik.com + editor.buildrik.com manage karna
  • Tab switch UX — user new tab mein jaata hai editor ke liye
  • API duplication — editor mein fetch calls banana for tRPC endpoints
  • State sync — dashboard aur editor ke beech state changes sync karna (e.g., site renamed)
  • DevOps overhead — do CI/CD pipelines, do builds, do monitoring setups

Summary

Criteria Option A Option B
Ship time 3-6 weeks 1-2 weeks
Risk level High Low
User experience Seamless Tab switch
Auth complexity None (shared) Cookie sharing
Editor code changes Major rewrite Minimal
Future flexibility Locked together Independent
Bundle size impact Dashboard +2MB No impact
