Lesson 04 · One component system

Kai agents, ek repo

Sawal: "editor par kai alag agents ke saath kaam kar sakta hoon?" Jawab haan — aur aap ne is ka poora system May 2026 mein khud likh liya tha, phir kabhi chalaya nahi. Ye lesson wo system nikaal kar, is arc ke liye theek karta hai.

Pehle: aap ke paas already kya hai

$ git worktree list

/Users/shahg/Desktop/pencil/buildrik-inspector-hardening  [inspector-hardening]

Chaar sibling trees. Saath mein teen documents jo main par pare hain: ek design spec, ek setup plan, aur ek copy/paste runbook — plus TASKS_LANE_A.md aur TASKS_LANE_B.md.

Sab kuch banaya, chalaya kabhi nahi Dono lane files ka aakhri commit 2026-05-21 chore(workflow): add parallel session task queues hai. Us din banayi, us din ke baad ek bhi edit nahi. sandbox-b ka node_modules tak install nahi hua. Ye "naya system banao" wala kaam nahi hai — ye "jo pehle se hai use chalao" wala kaam hai.

Asal unit agent nahi hai — file hai

Ye poore mauzu ka markaz hai. Do agents ek hi tree mein alag-alag files likh rahe hain — bilkul safe. Do agents ek hi file likh rahe hain — jo baad mein likhega wo pehle wale ko mita dega, chupke se, bina kisi error ke. Git ko pata bhi nahi chalega, kyunki dono ek hi working tree hain, do commits nahi.

Isi liye teen mechanisms hain, teen alag qeematon par:

MechanismKya alag hota haiSetupKab
Subagents
(ek tree)		 Sirf context. Tree, branch, node_modules, port — sab share. 0 Files disjoint hon. Dev server ki zaroorat na ho.
Worktree
git worktree add		 Poora tree + apni branch. Ek hi .git share. pnpm install, alag port, .env.local copy Dev server / test suite chahiye, ya shared file likhni hai.
Alag terminal session Upar wala + apni queue file + merge cadence. Upar wala + lane file + nightly squash Kai din ka autonomous kaam. Aap sirf log parhein.

Alag folders, alag panels, aapas mein koi taluq nahi. Aur wo ek file jise har conversion chhoo sakti hai — chrome-ui/index.ts — pichle 30 din mein sirf 2 commits mein badli. Yani zyada tar conversions maujooda atom hi reuse karti hain, nayi export add nahi karti.

Faisla Is arc ke liye worktree ki zaroorat nahi. Ek tree, kai subagents, ek agent = ek file. Setup zero. Worktree tab nikaalein jab do lane sach much alag branches par chahiye hon.

Jo cheez tootegi: baseline file

Yahan asal khatra source files mein nahi hai. Wo hai scripts/.styling-baseline.json — ratchet ki yaaddasht. 

if (process.argv.includes("--update")) {
  writeFileSync(BASELINE_PATH, …)   // poori file, dobara likhi gayi
}

--update poori JSON ko apne tree ke count se dobara likhta hai. Ek tree mein ye theek hai. Worktrees mein ye zeher hai: 

worktree A → panel X drain kiya → --update → likha: "Y abhi bhi 18 par hai"
worktree B → panel Y drain kiya → --update → likha: "X abhi bhi 18 par hai"

merge → dono drains real hain, lekin baseline dono ko 18 par lock kar raha hai
      → ratchet PASS, 36 style ki dheel ke saath
      → koi error nahi. Taala dheela ho gaya, khamoshi se.
Qaeda Baseline ka sirf ek likhne wala hota hai. Agents drain karte hain; --update aap khud, sab merge hone ke baad, ek baar chalate hain. Ye qaeda naya nahi — aap ne May ke design mein MEMORY.md, package.json aur prisma migrations ke liye bilkul yehi likha tha: "single writer prevents merge corruption on a hot file". Baseline JSON usi list ki agli entry hai.

Worked example — 4 agents, abhi

Parent session (aap) pehle baseline record karta hai — is se agents ke paas "baseline check karne" ka bahana hi khatam ho jata hai:

$ node scripts/check-styling-ratchet.mjs > /tmp/baseline-before.txt
$ npx tsc --noEmit 2>&1 | grep -c "error TS" >> /tmp/baseline-before.txt

Phir har agent ko ek file, aur teen sakht qaede:

Convert src/editor/export/CodePreview.tsx to chrome-ui + `tw:` utilities.

- Sirf YEHI file likhein. Koi doosri file nahi.
- `--update` NA chalayein. `git commit` NA karein. Main karunga.
- `git stash` NA karein. Baseline pehle se /tmp/baseline-before.txt mein hai.
- Business logic na toote. Visual drift qabool hai.
- Wapis: kya hataya, aur konsa chrome-ui atom laga.

Sab wapis aane ke baad, aap ek baar:

$ pnpm test && pnpm run verify:ds        # 10 gates, ratchet un mein aakhri
$ node scripts/check-styling-ratchet.mjs --update
$ git commit -am "refactor(chrome): 4 panels drained — inline_literal 836 → …"
Qeemat, sach sach Aap ki apni memory se, 15 incidents par: parallel dispatch mein ~30-50% agents phir bhi git stash chala dete hain — chahe prompt mein saaf mana kiya ho. Har incident ~10 min recovery. 4 agents = ~1-2 stash incidents ka hisab rakh kar chalein. Ye rukta nahi; sirf sasta hota hai jab baseline pehle se file mein likhi ho.

Aap ne 4 panels 4 alag worktrees mein drain karwaye. Har agent ne apna kaam poora kar diya. Ab?

Baseline poore tree ka snapshot hai, ek panel ka nahi. Har worktree ka --update baqi teen panels ke purane numbers likh dega, aur merge ke baad wo dheel ban jayegi — bina kisi FAIL ke. Option 4 to ratchet ko hi khatam kar deta hai: baseline nahi to muqabla kis se?

Kab worktree sach much chahiye

HalatEk tree kaafi?
Alag-alag panel files convert karnaHaan
Dono ko dev server chahiye (5050 / 5051)Nahi — worktree
Ek lane main par, doosri risky branch parNahi — worktree
Baseline dekhna hai bina apna kaam kho'eNahi — worktree (stash kabhi nahi)
Kai din ka autonomous kaam, alag queuesNahi — poori lane setup
Worktree ki chhupi qeemat node_modules 1.9G ka hai. pnpm store se hardlink karta hai to disk kam lagti hai, par install phir bhi minute leti hai — aur is repo mein pnpm 11 fresh worktree mein build scripts skip kar deta hai, yani prisma generate haath se chalana parta hai aur linux sharp graft karni parti hai. Isi liye default ek tree hai.

Ek line mein

Agents baantein files ke hisab se, trees ke hisab se nahi. Tree tab torein jab do agents ko alag branch ya alag port chahiye ho. Aur jo bhi shakl ho — ratchet ki baseline ka likhne wala hamesha ek hi rehta hai: aap.
