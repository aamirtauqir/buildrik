### Detailed Finding Breakdowns

#### B-01 — CMS buried 3 clicks deep [CRITICAL]

```
OBSERVATION
  `tabsConfig.ts` has 10 tabs. No "cms" tab exists.
  CMS access path: Settings (click) → Integrations sub-screen (click) → Collection Setup Modal (click)
  = 3 clicks minimum. CMS Preview Bar exists but only shows when bindings already exist.

USER IMPACT
  The Content Manager persona (one of 4 primary personas) works in CMS data daily.
  3 clicks to reach their primary tool, every session, is a constant friction tax.
  They have no way to see existing collections without going through Settings.

ROOT CAUSE
  IA / User Journey: CMS was implemented as a Settings sub-feature
  (integration), not as a first-class creative tool alongside Pages and Media.
  The PRD explicitly identified this gap: "A dedicated Rail entry reduces
  access from 3 clicks to 1 for the content manager persona."

RECOMMENDATION
  Add a "CMS" tab to the Rail top zone (between Pages and Components).
  Panel shows: collection list, item counts, "+ Add item" per collection,
  link to Collection Setup Modal. Matches PRD screen 17 spec.
```

#### B-02 — No Team Flow in Onboarding [CRITICAL]

```
OBSERVATION
  `useOnboardingOrchestrator.ts` has a single OnboardingPhase: "active" | "done".
  `loadInitialPhase()` reads localStorage only — no check for project state
  (page count, element count, collaborator count).
  A user joining an existing 50-page team project gets the same solo
  "add your first element" checklist as a brand new user.

USER IMPACT
  Team member opens a project for the first time. They see:
  "Create your first page" (already has 50) — irrelevant.
  "Add an element" — already thousands of them.
  The onboarding actively contradicts their reality. Breaks trust in the tool.
  They dismiss onboarding permanently and miss the team-specific guidance
  (team component library, design system tokens, presence avatars).

ROOT CAUSE
  Onboarding / Personas: A single flow was built assuming solo usage.
  The PRD defines two distinct flows: Solo (empty project) and Team
  (existing project with content). The detection logic was never implemented.

RECOMMENDATION
  In `useOnboardingOrchestrator`, on init: check Composer for project state
  (element count > 0, page count > 1, collaborators > 0). If "team project"
  detected → use Team flow (3 checklist items, abbreviated spotlight, project
  summary in welcome modal). If "solo" → existing flow unchanged.
```

#### B-03 — Export Modal missing Code Quality Score [HIGH]

```
OBSERVATION
  `ExportModal.tsx` has 3 tabs: preview / code / options.
  ExportResult type has `success` and `error` fields but no quality scoring.
  No component in `src/editor/export/` contains "quality", "score", or "checklist".

USER IMPACT
  Developers receiving exported code have no confidence signal.
  PRD design principle 4: "Export quality is the moat — generated code must
  satisfy a senior React developer." Without the score, designers have no
  feedback loop and handoff is a black box.

ROOT CAUSE
  Feature was scoped out or not yet implemented. The export engine
  (`ExportEngine`) processes the pipeline but doesn't surface quality metrics
  to the UI.

RECOMMENDATION
  Add a CodeQualityScore component inside ExportModal above the preview/code
  tabs. 0–100 score bar + 5 checklist items (component structure, CSS custom
  props, semantic HTML, accessibility, code cleanliness). Score calculates
  from ExportResult data.
```

#### B-04 — Design System missing Brand Setup Wizard [HIGH]

```
OBSERVATION
  `features/design-system/ui/` contains: DesignSystemTab, ColorTokenList,
  TypeTokenList, SpacingTokenList, ExportDropdown, ReviewModal, DraftChip,
  AddTokenModal, TabGuardModal. No wizard, no brand setup, no logo upload.

USER IMPACT
  First-time users open the Design System tab and see a raw token list
  (Primary: #2563EB, Secondary: #64748B, etc.) — Aquibra's defaults.
  There's no guided path to replace these with the team's actual brand colors.
  Time to brand setup is high; teams ship with default blue tokens they never
  meant to use.

ROOT CAUSE
  The Brand Setup Wizard was specified in the PRD but not implemented.
  It requires: logo upload → AI dominant color extraction → palette preview
  → font selection → token population.

RECOMMENDATION
  On first open of Design System tab (detect via localStorage flag), show
  an overlay wizard:
  Step 1: Upload logo → AI extracts dominant colors
  Step 2: Confirm/adjust generated palette (5–7 colors)
  Step 3: Choose heading + body fonts from Google Fonts
  Step 4: Tokens auto-populated, wizard dismissed
  "Skip" button available at all steps.
```

#### B-05 — Design System missing Lock Tokens [HIGH]

```
OBSERVATION
  No lock toggle found in `DesignSystemTab.tsx` or any design-system UI file.
  The ExportDropdown, ReviewModal, DraftChip, TabGuardModal all exist but
  none implement a lock/unlock mechanism.

USER IMPACT
  On a 4-person design team, any member can accidentally change the brand
  primary color mid-sprint. Since token changes auto-apply in real-time to
  all elements, a stray edit silently propagates to the entire project.
  No recovery path except undo, which only works in the same session.

ROOT CAUSE
  Feature not yet implemented. PRD specifies: lock toggle in the tab header,
  visible to all team members, only the locking user or Owner can unlock.

RECOMMENDATION
  Add a 🔒 toggle button to the DesignSystemTab header (right side).
  When locked: all token value fields become read-only, "Locked by [user]"
  tooltip shown on hover. When the non-locking user tries to edit:
  "Tokens locked by Shah. Ask them to unlock." Only locking user or Owner
  can click to unlock.
```

#### B-06 — Build Tab Favorites are browser-local [HIGH]

```
OBSERVATION
  `BuildTab.tsx:46-51`: when first favoriting an element, toast shows:
  "Favorites are saved in this browser only."
  FavZone persists to localStorage, not SyncManager.

USER IMPACT
  Designer A favorites "Hero Section" on their laptop.
  Designer B on the same project has no shared favorites — they see empty.
  The "Team Favorites" concept from the PRD is broken: teams get zero benefit
  from a shared element library. Every designer maintains their own isolated list.

ROOT CAUSE
  Favorites were implemented with localStorage as the storage backend.
  PRD requires SyncManager team sync (with localStorage fallback for solo projects).
  The build tab hook (`useBuildTab`) needs to detect collaboration context
  and switch storage backends.

RECOMMENDATION
  In `useBuildTab.ts`: check if `composer?.sync` is available (team project).
  If yes → read/write favorites via SyncManager (shared team state).
  If no → localStorage fallback (solo project, current behavior).
  Update the toast: "Added to team favorites — synced across your team."
```

#### B-07 — Rail bottom zone mental model mismatch [MEDIUM]

```
OBSERVATION
  `tabsConfig.ts` bottom zone contains: design, settings, publish, history.
  "Design" (Design System — a creative tool for brand tokens) is grouped
  with "Settings" (site config), "Publish" (deploy action), and "History"
  (version management) — three project-management tools.

USER IMPACT
  A designer doing creative work (switching between canvas and design tokens
  frequently) must keep going to the "project config section" to access
  brand tokens. The visual grouping implies Design System = administrative tool.
  It breaks the flow between the two most commonly paired tasks:
  Canvas editing ↔ Design System token editing.

ROOT CAUSE
  IA: Design System was added to the bottom zone because it "configures"
  the project. But the user's mental model is: Design System = design tool,
  Settings = project configuration. These serve different workflows.

RECOMMENDATION
  Split bottom zone into two groups:
  GROUP A — Creative tools (near top): Design System (moved up, near canvas tools)
  GROUP B — Project config (at bottom): Settings | Publish | History
  Add a visual divider between the two groups in the bottom zone.
  OR: Move Design System to top zone entirely (after Components).
```

### F-02 — Duplicate Subscription Pattern (Semantic Duplication)

**FILE:** `useMediaManager.ts:42–61`, `useTemplateManager.ts:40–60`, `useDataManager.ts:30–49`

**SMELL TYPE:** Duplicate logic / Semantic duplication

**WHAT'S HAPPENING:**
The exact same event-subscription pattern appears three times independently across three hooks:

```ts
// Verbatim pattern in all three files:
const updateState = () => setSomething(composer.manager.getAll());
composer.manager.on(EVENT_1, updateState);
composer.manager.on(EVENT_2, updateState);

};
```

**IMPACT:**
- Bug in subscription teardown = fix in 3 places
- Memory leak pattern (if off() is missed) gets copy-pasted
- No single source of truth for "how to subscribe to composer state"
- Violates CLAUDE.md rule #3 ("Duplicate logic NAHI")

**REFACTOR:**
Extract shared factory to `shared/hooks/useComposerState.ts`:

```ts
export function useComposerState<T>(
  composer: Composer | null,
  selector: (c: Composer) => T,
  events: string[]
): T | undefined {
  const [state, setState] = useState<T | undefined>(
    () => (composer ? selector(composer) : undefined)
  );
  useEffect(() => {
    if (!composer) return;
    const update = () => setState(selector(composer));
    events.forEach(evt => composer.on(evt, update));
    return () => events.forEach(evt => composer.off(evt, update));
  }, [composer, events]);
  return state;
}
```

Used in all three existing hooks. This is 1 implementation instead of 3.
