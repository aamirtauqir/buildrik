## OVR-W01 — asynchronous conflict sits outside shared overlay ordering

**Severity:** P2 candidate. **Status:** PARTIAL; source reachability established, browser outcome NOT RUNTIME VERIFIED.

**Source sequence:** Open a standard editor dialog, then receive `SAVE_CONFLICT_EVENT`. `packages/editor/src/editor/shell/AquibraStudio.tsx:354` sets conflict without closing or suspending existing StudioModals; both remain rendered. `packages/editor/src/editor/shell/modals/ConflictModal.tsx:33` uses z-index 2147483646 in local markup (line 45), not the shared body-appended root. It supplies scrim/action close callbacks but no shared Escape owner. Meanwhile `packages/editor/src/editor/chrome-ui/focus.ts:66` selects topmost by document order, not visual stacking order. When the shared overlay root follows the editor mount in the body, the lower visual dialog can remain the final DOM modal, so Escape can dismiss it behind the visible conflict dialog.

**Expected:** A new asynchronous interruption should either become the active overlay with consistent close ownership, or explicitly suspend the previous overlay and restore it afterward. Background modal dismissal should not depend on where the two rendering roots occur in the document.

**Root cause / affected modules:** Conflict's deliberate standalone rendering and the shared trap's DOM-order assumption have no common active-overlay arbitration. Affects conflict handling plus whichever standard dialog was already open, not every menu or dashboard dialog.

**CHANGE only after reproduction:** Test one shared modal → simulated conflict → Escape → dismiss conflict; record which dialog closes and whether the original dialog remains. Verify production DOM-root order and stacking contexts first. If confirmed, align active close ownership across standalone interruptions and shared overlays without forcing intentional picker-child stacks into single-modal behavior. No implementation change is proposed in this source-only pass.
