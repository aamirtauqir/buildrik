## Reconciliation

- The editor palette searches commands/actions/navigation; it intentionally does not index current page entities. The canvas palette searches its own canvas command list. They are separate entry contexts and do not establish two remote search engines.
- “Search Listings” in Pages is the named SEO audit table with PAGE/TITLE/DESC/SCORE columns. It should not be counted as a search control merely because of its destination label.
- Quick Assets and Full Library share data and search logic; their different surface role is intentional. The placeholder/scope mismatch in Full Library is the sole new editor search finding from this pass.
- No authenticated database search, large catalog benchmark, every placeholder copy, or every picker interaction was verified. Search reports remain source-qualified where runtime was unavailable.

## SRCH-E01 — Full Library search copy promises wider scope than its active folder predicate

- **Priority:** P2 candidate; **source verified**, runtime NOT VERIFIED due to the pre-existing LibraryManager compile blocker.
- **Evidence:** Full Library exposes placeholder “Search across all folders…” (`src/editor/media/LibraryManager.tsx:811`). `useLibraryState` filters `libraryItems` by `currentFolderId` before applying the query (`:167`–`:184`); `setLibrarySearch` only changes query (`:258`). The remote search path imports matches but renders them through that same folder-scoped derived list.
- **Expected behavior:** Query scope and visible folder scope should agree. If search is global, matches from outside the open folder must surface with their folder context; if folder-local, the placeholder should say so and indicate the active folder.
- **Recommendation:** Product/UX confirm intended scope, then align either query scope or copy and verify a known matching asset in another folder. Do not conflate this with the backend’s paginated search cap or the dashboard Media pagination findings.
