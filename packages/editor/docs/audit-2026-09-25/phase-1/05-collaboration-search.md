## SC-C01 — Team member browsing stops at20 despite supported25-member plan

- **Priority:** P2. **Disposition:** CHANGE. **Status:** VERIFIED STATIC / NOT RUNTIME VERIFIED.
- **Evidence:** `packages/dashboard/app/dashboard/settings/team/page.tsx:24` always requests `{page:1,perPage:20}`. `server/services/team.service.ts:46` and `:47` use page skip/take, sorted newest joined at `:48`. The page passes `membersQuery.data.data` to MembersTable (`:188`) without pagination callbacks/total; the inspected page/table have no member-search input or continuation control. `lib/constants/plan-limits.ts:73` permits25 team members for BUSINESS.
- **Impact:** Once a supported workspace has21–25 members, older rows are excluded from the only inspected Team management table request; they cannot be found there through browsing, filtering or search. This is conditional source-derived behavior, not an observed production dataset.
- **Root cause:** Paginated service contract is consumed as a complete single-page list.
- **Recommendation:** Expose page/continuation state and relevant total in Team. Add server-backed name/email search only if desired, and apply it before pagination; do not merely filter the first20 locally.
- **Correct owner:** Workspace Team collection retrieval, not presence or Review.

## SC-C02 — Full Activity/inbox destinations expose fixed recent subsets

- **Priority:** P2. **Disposition:** CHANGE. **Status:** VERIFIED STATIC / NOT RUNTIME VERIFIED.
- **Activity evidence:** Dashboard home links to `/dashboard/activity` (`packages/dashboard/app/dashboard/page.tsx:261`). Destination calls `trpc.dashboard.activity({filter})` (`activity/page.tsx:21`). Router `server/trpc/routers/dashboard.ts:58` accepts only all/mine/team; calls `getActivityFeed` without limit/offset (`:69`). Actual implementation `server/services/dashboard.service.ts:134` defaults limit20 and offset0, applied at `:144`. Destination has no pagination controls. The separately available `activity-log.service.listWorkspaceActivity` is not this call chain.
- **Notification evidence:** Editor “See all notifications” (`NotificationPanel.tsx:353`) leads to the page that calls `notifications.listGrouped` (`packages/dashboard/components/notifications/notification-page.tsx:22`). The procedure (`server/trpc/routers/notifications.ts:44`) accepts filter only. `notification.service.ts:87` takes50 rows and returns `{groups}` at `:124`, without a next cursor/count. Expanding groups reveals only those already fetched rows. A separate paginated notifications.list endpoint exists but is not this page's query.
- **Impact:** Users cannot browse or find matching records older than each route's fixed window through these full destinations. Filters are evaluated before the cap, so Unread/Mine can retrieve older matches than All; this does not make any filter complete beyond its own cap.
- **Root cause:** Full destination reuses a bounded feed contract without continuation or accurately limited scope.
- **Recommendation:** Give the full destinations pagination/cursor retrieval and accurate totals or next-page state, or explicitly define them as recent-only and provide the promised history elsewhere. Optional text search must execute against the complete authorized dataset before pagination. Keep quick bell/home excerpts intentionally bounded.
- **Correct owners:** Notifications and dashboard Activity collection APIs/UI. This shared omission has separate service implementations; do not require a new generic search subsystem to fix it.

## Duplicate and necessity conclusions

### SC-C03 — Global Team search filters only the10 newest members

- **Priority:** P2. **Disposition:** CHANGE. **Status:** VERIFIED STATIC / NOT RUNTIME VERIFIED. The workspace-search specialist identified this candidate and this pass traced its user dataset/limit.
- **Evidence:** `packages/dashboard/components/search/command-palette.tsx:127` advertises a Team scope; `:442` labels the input “Search or jump to...” with aria-label “Search Buildrick”. When term length is at least2 and scope allows Team (`:188`, `:212`), `:220` requests `team.list({page:1,perPage:10})`. `:293` filters only that returned page by `fullName`/`email` and `:302` slices matches to5. `server/services/team.service.ts:46` applies the10-row database limit before the palette term is evaluated and orders newest joined first at `:48`.
- **Impact:** A supported11–25-member workspace can have an exact name/email match outside the newest10 that this global Team search cannot return. No UI copy limits the scope to recent10. A no-results outcome is thus not evidence no matching member exists in the workspace.
- **Root cause:** Result-display limit is confused with the searchable candidate set. This is related to SC-C01's fixed-page consumption but is a distinct search path with a10-row threshold.
- **Recommendation:** Add validated member name/email search to the Team list/search service and filter before pagination/limit; keep a small ranked result list in the palette. Do not fetch an arbitrary first page then advertise all-Team search. Coordinate with workspace palette owner; its separate Pages guard finding is not duplicated here.

History's single query intentionally follows Saves versus Changes; the placeholder changes with the active dataset and Published suppresses the field. It is not a duplicate global search or a dead Published search. Notification preview sorting is only within latest5; agency queues paginate, so their initial50 are not terminal caps. Flat site comments load without a cap but offer grouping, not textual lookup; no product requirement was found that would justify automatically adding comment search.

Invite site picker cap50 currently matches the configured maximum plan50. This was checked before classifying reachability: no unsupported >50 finding is reported. Presence has no workspace-user retrieval function, and invite email/name/share-link name inputs are authoring controls rather than search.
