## Deep-link chain verification

### History approval comparison → Review Compare

Producer: `packages/editor/src/editor/sidebar/tabs/history/components/SavesChrome.tsx:140` emits `EVENTS.UI_PANEL_OPEN` with both panel and screen. Consumer: `shell/hooks/useEditorEventListeners.ts:145` derives accepted panel IDs from the tab registry; handler `:155` forwards both fields to `openLeftPanelToTab`. State: `useStudioState.ts:317` opens drawer, sets primary tab and retains nonempty sub-screen. Shell passes the selected tab's sub-screen at `AquibraStudio.tsx:554`; `StudioPanels.tsx:480` carries it to LeftSidebar; `LeftSidebar.tsx:712` keys render on both tab and sub-screen. Router `TabRouter.tsx:251` converts it to `initialCompare`, which `ReviewTab.tsx:343` consumes via `openCompare()`.

Thus the first deep-link chain is implemented; this is not an emitted-but-unconsumed screen parameter. Back uses `setCompareOpen(false)` (`ReviewTab.tsx:554`), leaving the persisted screen request unchanged; see NAV-C01.

### Site activity → matching actual DOM anchor

Producer: `SiteMenu.tsx:225` opens `#activity-log`. Destination: dashboard `components/site-detail/overview-tab.tsx:306` passes `id="activity-log"` into `SectionCard`. The primitive (`components/dashboard/primitives/section-card.tsx:30`) writes that `id` to the actual `<section>`. The section exists regardless of whether activity is empty. The site layout first waits on site query (`app/dashboard/sites/[id]/layout.tsx:34`), so actual scrolling after asynchronous load is **NOT RUNTIME VERIFIED**, but a mismatched/nonexistent source anchor is ruled out.

### Panel Close vs navigation

`LeftSidebar.tsx:626` creates common props with `onClose: onDrawerToggle`; TabRouter spreads them into History and Review. Their Close controls dismiss the panel. Review Compare's Back returns to Review list; an external entry from History is not recorded as a return stack. This is a concrete hierarchy decision rather than an inferred browser-history implementation.

## Findings

### NAV-C01 — One-time Review Compare request remains stored as navigation state

- **Priority:** P2. **Disposition:** CHANGE candidate. **Status:** source mechanism VERIFIED; user-visible reproduction PARTIAL / NOT RUNTIME VERIFIED.
- **Evidence:** `useStudioState.ts:317` changes sub-screen only when `subTab` is truthy; a generic `openLeftPanelToTab("review")` leaves previous `review:"compare"` intact. The sub-screen record is persisted with panel state (`useStudioState.ts:272`). `ReviewTab.tsx:342` uses a per-mount `compareRequested` ref; `:345` marks the request consumed once. Back (`:554`) only changes local compareOpen. LeftSidebar remount key (`:712`) changes only when tab/sub-screen value changes.
- **Predicted reproduction A:** Deep-link into Review Compare → Back to Review → another tab → plain Site menu Review. The stale `compare` sub-screen remounts Review with initialCompare true, opening comparison rather than generic Review list.
- **Predicted reproduction B:** Deep-link into Review Compare → Back → click ReviewBar Compare while Review remains mounted. The same tab/sub-screen values do not constitute a fresh request and compareRequested is already true, so no reopened comparison is expected.
- **Expected navigation:** Explicit Compare shortcuts open Compare each time; plain Review opens the intended current/list destination without replaying a consumed transient request.
- **Root cause:** Transient navigation intent and persistent location share one string with no consumption/reset handshake.
- **Recommendation:** Separate request consumption from remembered tab preference, or clear/acknowledge one-time Compare intent when handled/backed out. Validate History Published under the same state mechanism before generalizing the change. Do not change all remembered tabs indiscriminately.

### NAV-C02 — Clickable issue rows dismiss without reaching their target

- **Priority:** P2. **Disposition:** CHANGE. **Status:** VERIFIED STATIC / NOT RUNTIME VERIFIED.
- **Evidence:** `IssuesPanel.tsx:265` renders interactive Row; `:269` invokes `onSelectElement(i.id)`. Its actual shell callback is `AquibraStudio.tsx:626`, `onSelectElement={() => setIssuesOpen(false)}`. Current generated issues already carry tokenId and `Brand › tokenId` location (`AquibraStudio.tsx:314` through `:320`), but the row does not navigate to Brand or select anything.
- **Expected navigation:** A clickable finding takes the user to its resolvable target, or is plainly non-navigational. Close remains an explicit dismissal action.
- **Root cause:** Presentation offers target navigation while shell supplies only dismissal; issue ID is not a valid universal element target.
- **Affected modules:** Issues, shell, Brand/design-system target routing; future element/page issue producers.
- **Recommendation:** Route known token findings to their correct Brand context using explicit target metadata, or remove navigation affordance where no destination exists. Do not pass arbitrary issue ID into element selection.
