## IA findings and decisions

### IA-C01 — Draft-sharing entry owns published-site sharing

- **Severity:** P2. **Disposition:** CHANGE. **Status:** VERIFIED STATIC; NOT RUNTIME VERIFIED.
- **Expected owner:** Published-site sharing for an existing public deployment; snapshot Review when the job is client review of unpublished work.
- **Current owner:** Editor site-menu “Share preview link” → dashboard `ShareDraftModal`, whose title/action promise a draft link.
- **Evidence:** `packages/editor/src/editor/shell/SiteMenu.tsx:275` routes the preview action to dashboard site detail. `packages/dashboard/components/site-detail/site-header.tsx:41` opens the sharing modal from that query. `share-draft-modal.tsx:69` says “Share Draft”; `:81` says “Create draft link”, but its body at `:104` says it opens the published site. `packages/dashboard/app/share/[token]/page.tsx:25` selects `publishedUrl`; `:39` calls `shareDestination`; `:41` renders not-published when there is no destination. `lib/share-destination.ts:16` returns only `site.publishedUrl ?? null`.
- **Root cause:** Product entry naming still assigns draft/preview responsibility to a published-destination link owner. The implementation now explains the narrower scope in body text, but the primary category remains contradictory.
- **Affected modules/dependencies:** Editor site menu, dashboard site-detail sharing, public share route; separate review snapshot flow. Existing links and backend behavior need not change for an IA correction.
- **Recommendation:** Name this path for published-site sharing consistently. Keep unpublished snapshot review with Review; do not introduce a new draft renderer as an incidental IA fix.

### IA-C02 — Review currently uses the left sidebar despite the playbook’s right-side review category

- **Severity:** P2 decision item, not a confirmed defect. **Disposition/Status:** PRODUCT DECISION REQUIRED; NOT RUNTIME VERIFIED.
- **Expected owner under Prompt 1:** RIGHT for review/validation, or an explicitly approved global/site review workspace when snapshot/sign-off management exceeds selected-element scope.
- **Current owner:** Site-scoped `ReviewTab` routed through the left panel.
- **Evidence:** `AquibraStudio.tsx:518` calls `state.openLeftPanelToTab("review")`; `:536` opens the same tab’s Compare state. `TabRouter.tsx:243` renders `ReviewTab`. `rail/tabsConfig.ts:238` assigns `tool: "site"` and no rail zone. The current data contract is site-wide: `ReviewTab.tsx:200` fetches current round and site comments, with no selected-element parameter. The menu doorway is always provided outside read-only view at `StudioHeader.tsx:819`.
- **Root cause:** Existing site-workflow IA and the requested left/right classification differ. There is no evidence that moving site-wide sign-off into selected-element Inspector is automatically correct.
- **Affected modules/dependencies:** Shell panel router, site menu/review pill, canvas comments, snapshot Compare, approval-dependent Publish.
- **Recommendation:** Orchestrator records and resolves the intended review surface before proposing relocation. Preserve the distinction between contextual pins and global site approval.

## Verified ownership boundaries to retain

- Canvas comment pins and Review consume the same comments API/model. Their shared read/write source supports two context-specific surfaces rather than establishing duplicate persistence.
- Editor `ActivityView` is an undo-history UI. Dashboard Activity reads persisted workspace activity. These should remain separately named and owned; the code filename is not evidence they compete.
- Team invitation is workspace administration; share links address a site destination; external review uses a frozen site snapshot and token. These are three distinct jobs with three distinct owners.
- Realtime/session state is engine-owned; presence is global shell presentation. Neither owner is the asynchronous Review service.

### IA-C03 — Notifications categorizes account/security/billing events as Mentions

- **Severity:** P2. **Disposition:** CHANGE. **Status:** VERIFIED STATIC; NOT RUNTIME VERIFIED.
- **Expected owner/category:** Personally directed account/security/billing notices under a matching notification category; collaboration mentions would require an actual directed comment/mention capability.
- **Current owner:** Dashboard notification inbox filter named Mentions.
- **Evidence:** `packages/dashboard/components/notifications/notification-page.tsx:13` labels the `mentions` filter “Mentions” and passes it to `notifications.listGrouped` at `:22`. `server/services/notification.service.ts:82` filters by `MENTION_NOTIFICATION_TYPES`. The executable constant at `packages/shared/schemas/notifications.ts:13` consists of `SECURITY_PASSWORD_CHANGED`, `SECURITY_2FA_CHANGED`, `SECURITY_LOGIN_NEW_DEVICE`, and `PAYMENT_FAILED`. This is the category's actual data source, irrespective of comments describing it as directed-at-you.
- **Root cause:** “Mentions” labels a different event taxonomy from collaborative references to a person.
- **Affected modules/dependencies:** Dashboard notifications filter and shared notification classification. No comment model or delivery feature is required to correct the category name.
- **Recommendation:** Name the current category to reflect its included events, or remove the extra category if All/Unread is sufficient. Do not present the existing filter as evidence of comment mentions.

### Supported discussion model

The review composer at `packages/editor/src/editor/sidebar/tabs/review/ReviewTab.tsx:255` calls `postReply(body, activePage)` at `:261`; `services/ReviewService.ts:277` issues `comments.create({ siteId, body, pageId })`. `server/services/comment.service.ts:22` writes body/page/coordinates/selector into a new `Comment`, and `:49` lists by site/status in creation order. The complete create schema (`packages/shared/schemas/comments.ts:10`) and model (`prisma/schema.prisma:474`) contain no parent comment, recipient/mention list, or review-round field. The textarea at `ReviewTab.tsx:963` binds a plain string. Therefore this path implements a flat site/page discussion and internal notes, not nested reply relationships or structured mentions.

The external client has a different reading scope: `server/services/client-review.service.ts:227` writes a comment with `reviewerId`; `:257` lists only `{ siteId, reviewerId }`. An editor reply gets `authorId` through `comments.create` and is not returned by that client list. This clarifies the existing “Replies are internal notes” statement at `ReviewTab.tsx:973`; the nearby placeholder “Reply to the client…” at `:967` should not be treated as implementation proof of a client-visible messaging channel. This is a scope clarification for IA; channel-label refinement can be reconciled in the later semantics audit.

Narrow source searches for mention/thread/reply/parent covered the editor Review and canvas comments, ReviewService, dashboard comments/reviews and token review route, comment/client-review/review services, shared comment/review schemas and Prisma model.
