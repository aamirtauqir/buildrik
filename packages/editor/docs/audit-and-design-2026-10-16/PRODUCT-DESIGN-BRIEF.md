### Phase 1 — approved capability-preservation rule

> No feature will be silently deleted. Every existing feature must receive a documented **Keep, Move, Merge, Redesign, Restore, Fix, or Defer** decision.

The preserved unit is a **user capability with its meaningful behavior**, not every old button or pixel arrangement. Preserve eligibility, supported values/units, references, persistence, recovery and discoverable task completion. Correct bugs intentionally; do not preserve a known defect as a compatibility requirement.

| Decision | Meaning | Mandatory evidence / preservation requirement |
|---|---|---|
| **Keep** | Retain the supported task, owner and primary home | Record current entry, eligibility, behavior and regression criteria. Keep is not proof that every edge case works |
| **Move** | Relocate the task without changing its data ownership or intended effect | Name old/new entries, exact target, return, shortcuts/deep links, focus and preserved draft/context. Navigation alone must not mutate authored content |
| **Merge** | Consolidate interfaces for the same task and authoritative value | Prove equivalent owner, scope and write semantics; name the surviving home and preserve unique options, advanced values and recovery. Management, application and override are not automatically duplicates |
| **Redesign** | Rework a task's structure or behavior because its present workflow is unsuitable | Provide the full before/after capability map, owner, flow, states, compatibility effects and acceptance criteria. A cleaner layout alone is insufficient |
| **Restore** | Reintroduce a previously supported, now removed or inaccessible user capability | Identify the former usable path, why restoration is justified, intended new path and compatibility. Engine APIs alone do not establish a former UI; creating a first UI requires an explicit new-capability decision |
| **Fix** | Correct an established failure while preserving the intended capability | Link a bounded defect record, baseline/source evidence, expected behavior, regression checks and recovery/output impact. An unverified report remains **Fix candidate / verification pending**, not a proven failure or completed fix |
| **Defer** | Deliberately postpone specified design or implementation work | Name exactly what is deferred, why, current availability, safe interim behavior, dependencies, and a concrete revisit trigger. Preserve existing routes/data/permissions. Defer is not permission to hide/remove a usable feature or waive a release-blocking defect |

These are **capability decisions**. Section 8's KEEP/EXTEND/REGROUP/RESIZE/REDESIGN/DEDICATED WORKSPACE describe a different dimension: the treatment of a panel. For example, a feature may be **Move** while its receiving panel is **REGROUP**. Neither label replaces the other.

Each atomic capability receives one primary decision; separate related work is linked, such as a **Move** record with an independent **Fix** dependency. Decision authority (**proposed / approved / superseded**), evidence (**source / runtime / unknown**) and delivery (**not implemented / implemented / verified**) are separate fields. **Pending classification** is an honest temporary workflow state, not an eighth disposition, and cannot satisfy Phase 1 completion. Lack of evidence is not a reason to blanket-mark the inventory Defer.

### Latest interaction refinements

These refinements are selected under FD-IA-09; their implementation and usability have not been verified. The detailed IA contracts below govern their exceptions and targets.

1. **Stable rail.** Keep tool/resource grouping and item order constant across workspaces. Identify the active destination with its label and a non-colour-only marker. Restricted destinations follow verified permissions; visibility must not grant access.
2. **Local workspace headers.** Keep collection, folder, category or settings-screen identity beside its relevant actions. Avoid adding module-specific actions to the global topbar. Define header overflow without hiding the main task.
3. **Exact return.** Back restores the immediate task origin, which may be Editor or a CMS field. Only Back to Editor restores the originating page, selection, breakpoint and canvas view. Explicit page selection opens the chosen page instead. Use a valid fallback if the target no longer exists; never change the write target silently.
4. **Explicit right-panel owner.** Show Heading, the selected asset name, or the selected CMS field as appropriate. Collapse optional detail when no resource needs it. Preserve existing useful page/no-selection editing in Editor until its separate audit decision is made.
5. **Specific status.** Prefer Page saved, Record saving, Upload failed or Sync pending over an ambiguous Saved. Show success only after the corresponding operation confirms it. When several operations coexist, prioritize failure/conflict/pending status and expose per-operation details from the status entry; do not let a successful page save conceal a failed record save. Saved and unpublished remain distinct. Copy follows the five save states — Saving… · Saved · Couldn't save — Retry · Applies on next publish · Offline — will save when back online (DS §3, CS-12) *(R-1018)*.
6. **Two canvas-control groups.** Editing contains document Undo/Redo and selected-element breadcrumbs; View contains breakpoint, viewport width, zoom, Fit and supported view options. At constrained widths, put secondary view options into View while keeping the active breakpoint and zoom visible. Use compact or collapsed breadcrumbs before clipping primary controls. GEO-01 sets the two-row toolbar threshold at canvas column <720px; View also hosts the contextual Record switcher / Show drafts / Show hidden elements (BD-22).

Do not introduce free docking as part of this refinement. Start with a predictable arrangement and bounded resize/collapse/restore; define focus, saved UI preference and canvas-budget behavior. Any already-supported equivalent capability must be mapped before changing it.

## 5. Core responsibilities

### 1. Understand the problem and goals

Identify the task failure, desired outcome, business relevance, and scope before drawing a new control. Distinguish a navigation problem from absent capability, a permission restriction, or an unavailable service.

### 2. Understand users and context

Consider expertise, habits, accessibility needs, project scale, permissions, and interruptions. Use explicit feedback as evidence. Label assumptions about frequency, preferences, or usability; never invent interviews or quotations.

### 3. Understand the existing product

Inspect module registrations, screens, contextual controls, schemas, write paths, and runtime behavior. Review selection-dependent and gated functionality before calling it missing. Maintain reviewed, partially reviewed, and not-reviewed coverage.

### 4. Organize information and navigation

Use tasks and resource ownership to establish hierarchy. Keep the user-confirmed rail destinations visible. Use consistent names in rail entries, headers, commands, help, and return links. Avoid competing destinations with unexplained differences.

### 5. Design complete flows

Describe entry, exact target, action, validation, feedback, completion, cancellation, failure, and return. Include interrupted and cross-module tasks. A collection of attractive default screens is not a complete flow.

### 6. Define ownership and boundaries

Separate selected-element properties, page configuration, shared resources, site settings, and workspace administration. Identify the authoritative value and write path. Resource ownership and permission ownership are different dimensions.

### 7. Reduce cognitive load

Keep frequent and consequential actions discoverable. Group related controls and disclose secondary complexity progressively. Explain scope near the action. Do not hide core modules or remove capabilities merely to make a screenshot simpler.

### 8. Define interaction and feedback

Specify selection, editing, validation, save timing, meaningful undo units, and recovery. Distinguish locally applied, queued, server-saved, previewed, and published states. Preserve input on recoverable failure.

### 9. Create consistent UI

Reuse suitable chrome components and existing tokens. Establish hierarchy through typography, spacing, alignment, restrained colour, and readable density. Keep editor chrome separate from the user's website Brand resources. Resolve contradictory documentation against current source and explicit user decisions; record remaining uncertainty.

### 10. Support accessibility and real contexts

Specify keyboard access, focus movement and restoration, understandable labels, non-colour-only feedback, contrast, and usable targets. Test long values, short windows, zoom, and realistic content. Provide alternatives to drag-only operations.

### 11. Design for growth

Give each new capability a canonical home. Reuse repeated interaction contracts without forcing unrelated workflows into one component. Plan large collections, long hierarchies, and resource search without growing permanent columns indefinitely.

### 12. Balance quality and feasibility

Separate presentation changes from behavior, schema, API, and persistence changes. Prioritize by impact, risk, confidence, and effort independently. Do not present a new class engine, multiplayer architecture, or agent system as a minor UI change.

### 13. Validate and hand off

Use evidence-backed walkthroughs, appropriately scoped prototypes, and usability feedback. Give engineering explicit flows, states, contracts, and tests. Review the resulting implementation separately when implementation is authorized; design-only work cannot establish a production pass.
