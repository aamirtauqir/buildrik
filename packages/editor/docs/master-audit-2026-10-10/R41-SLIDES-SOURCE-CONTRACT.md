## Protection, history and asynchronous consistency

Every SlidesSection mutation uses `writeElement` on the **slider parent** (`SlidesSection.tsx:89`). `src/engine/commands/commandOperations.ts:219` checks that target using writableElements, begins a named transaction and ends it in `finally`. Missing parent/locked parent means no write; the engine emits the established locked explanation. It does not check the chosen slide, its descendants or component ownership. The low-level duplicate/move/remove calls do not add the ordinary command-level protection guard. Normal delete/cut's stronger `dropLockedAndInstances` rejects component instances and locked descendants (`commandOperations.ts:40`).

**Proposed correction:** before delete or reorder, capture/revalidate parent ID, slide ID, membership, intended destination, current subtree protection and a structural revision. Block protected removal with a reason, and reject a stale/moved/deleted target before mutating anything. Confirmation must preview the named slide and its actual content. Parent lock should block all structural writes. Decide duplicate eligibility independently: copying readable locked content and mutating/removing that original are different operations; the current source checks only the slider. Do not invent a blanket permission rule without recording it as a proposed policy.

Transactions batch normal mutations but do not automatically prove isolated Undo or rollback. `writeElement` ends in `finally`, not rollback. `src/engine/Composer.ts:1263` captures an outer snapshot; `:1277` ends the transaction and notifies dirty state. `src/engine/HistoryManager.ts:85` sets a 500ms coalescing delay, and `:94` schedules history recording. SlidesSection does not use `runDiscrete`/flush before and after its handlers. Consequently, rapid operations may coalesce; one named transaction per handler is insufficient proof of one user-visible history step per click.

There is an important shell exception: `src/editor/shell/hooks/useClipboardToasts.ts:85` listens to duplicate bursts and calls `history.captureUndo()` at `:98`. `HistoryManager.ts:583` flushes pending history and returns a callback tied to that entry; it refuses a superseded action rather than undoing a newer edit. Thus duplication may get an explicit boundary through the mounted shell; direct delete/move do not have that local assurance. Actual shell timing must be tested before claiming runtime history behavior.

`HistoryManager.ts:205` avoids recording empty patches. Its `:516` Undo flushes pending work and restores the prior tree snapshot; `:427` preserves the current accessible page and `:596` re-resolves surviving selected IDs to new Element instances. The corrected finite design should snapshot only genuine changes, keep cancellation/no-ops out of history, and provide one-step recovery of exact logical membership/order/content. A logical slot+generation model and display variants are acceptable **prototype** evidence if explicitly distinguished from engine IDs, serialized subtrees and durable history.

`SlidesSection.tsx:78` refreshes on ELEMENT_UPDATED/CREATED/DELETED/MOVED; it does not subscribe directly to ELEMENT_DUPLICATED or HISTORY_UNDO. Duplication builds a tree through addChild; `src/engine/elements/ElementChildren.ts:99` itself emits no event. Broader Inspector/render subscriptions may still refresh the row. Treat post-duplicate/Undo read-back as a runtime check, not a conclusively established stale-UI failure from this observation alone.

## Carousel output is related but separate

The comment at `SlidesSection.tsx:6` saying carousel runtime is missing is stale. `src/engine/export/sliderRuntime.ts:61` implements it. It treats only direct children with class `buildrick-slide` as slides (`:66`), whereas SlidesSection counts all direct children. Imported non-slide children therefore require reconciliation; do not generalize a well-formed fixture to arbitrary Slider trees.

Runtime behavior: no initialization/control injection at zero or one slide (`sliderRuntime.ts:69`); modular index wrap (`:87`); arrows/dots according to attributes (`:74`); autoplay interval bounded to 1–60 seconds (`:75`); reduced motion prevents autoplay (`:159`); hover and focus pause it (`:165`). The block initially supplies two content-bearing slides (`src/blocks/Components/Slider.tsx:12`). This source does not establish independent configurable Loop or Pause-on-hover toggles merely because those labels exist in the register: wrapping and pause are built into this inspected runtime.

The canvas hook disables autoplay even when its attribute is true and remembers a **numeric index** keyed by slider ID (`src/editor/canvas/hooks/useSliderRuntime.ts:47`). Therefore source canvas does not prove autoplay-on output, and reordering can leave the same numeric index showing different slide content. Separate these three contexts in the design: selected Slider element, slide targeted by an edit, and carousel slide being previewed. If the corrected design keeps the same logical slide previewed after reorder, label that as intended behavior requiring runtime reconciliation.

## Finite design task and acceptance

Use root's native inventory and existing Slider shell/controls, per-slide menu, confirmation/recovery masters and layer conventions. The existing registered `Slides` field must lead into real slide membership actions; do not replace the entire source family with a 3↔4 count toggle.

1. **Initial:** three distinct logical slides A/Intro, B/Services, C/Contact, each with recognizable descendant content. Show their order in Settings and Layers and a visible corresponding slide preview. Slider/Settings/device is the return context. Structural order/content is shared across Desktop and Mobile.
2. **Duplicate selected:** duplicate B → `[A,B,B′,C]`. B′ has the same content but a new logical identity (new descendant identities in the intended implementation). Its row/thumbnail and count update. If showing a “copy” label, distinguish it from changing the customer's heading. One-step Undo restores `[A,B,C]` with C unchanged. Do not claim a newly duplicated slide was selected automatically by source; the section does not explicitly select it.
3. **Add:** with `[A,B,C]`, Add creates a new copy C′ after C, not a blank generic fourth card. An empty-slider Add fixture creates a new `New slide` instead. If the bounded pass omits empty/last-slide behavior, keep that leaf explicitly open rather than impose an invented minimum.
4. **Reorder:** move C before A → `[C,A,B]`, preserving the same identities/content. Undo restores order. Provide an explicit destination cue or accessible move action. Same-order/self/cancel/outside-drop leaves structure and the previous useful Undo snapshot unchanged. A source drop-before model must not be demonstrated as a swap.
5. **Delete:** target B by identity → `Delete Services slide?` with its content preview and a clear whole-slide consequence. Cancel/Escape/close retains everything. Confirm removes B only; one-step Undo restores B's original logical identity, subtree content and position. Later Add/Duplicate creates a new copy and never pretends it recovered B.
6. **Protection:** parent locked, removal subtree locked/protected, target moved/deleted and structural revision changed produce no-write explanations with a route back/review. A stale target must not silently become “whatever is now slide 2”. Source protection gaps remain implementation work even when the prototype models the correction.
7. **Return:** Close/reopen and Desktop/Mobile switch retain structural edits and the targeted Slider. Define preview behavior separately from selected element. A displayed preview identity stronger than source's numeric-index preservation is an explicit corrected-design choice.
8. **History boundaries:** one-step Undo restores complete finite pre-edit state; no-op and Cancel retain the preceding useful snapshot. Lock toggles or preview navigation excluded from that one-step model must be disclosed. Do not call a global `Undo last edit` a delete-specific recovery after newer actions; action-specific Undo must invalidate when superseded, matching captureUndo's intent.

For acceptance, independently inspect reactions, then visibly play representative duplicate/add/reorder/delete/Cancel/Undo and recovery outcomes. Check count, row order, Layers membership, visible content and logical identity, not labels alone. If using complete native specimens to avoid variable-visibility rendering bugs, map logical identity separately from the display-node aliases and verify exactly one intended specimen is visible. Do not count a new chooser destination or a missing-destination scan as task acceptance.

## Open runtime gates and evidence limits

- Real tree IDs/content/order and independent cloned data; DOM IDs, interaction targets, responsive/pseudo rules and CMS binding remapping across duplicate/delete/Undo.
- Last-slide/empty/imported invalid-child behavior, unrestricted slide counts and long/overflowing content.
- Parent/child/descendant locks, component restrictions, effective permissions, mixed selection and target revision changes.
- Native drag insertion/cancellation, after-last placement, keyboard alternatives, focus return and accessible announcements.
- Separate per-action history under rapid edits, superseded recovery, full Undo/Redo, exception rollback and autosave/reload.
- Canvas preview-index behavior after reorder/delete, exported runtime parity, actual timers, reduced motion, arrows/dots and focus/hover pause. Configurable Loop/Pause options need a source-backed decision.

None were rerun for this audit; no fresh test pass, browser outcome or engine parity is claimed.
