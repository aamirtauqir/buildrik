## Findings and hypotheses

### WS-01 — Failed media metadata/move writes can look locally successful (High, source-confirmed)

`src/services/AssetUploadService.ts:242` catches update errors and returns false; the move adapter does the same. `src/engine/media/MediaManager.ts:1359` first persists and updates local state, then ignores the boolean returned by `moveAsset` (`:1388`) and `updateAsset` (`:1435`), emits MEDIA_UPDATED and returns the updated asset. `useLibraryState.ts:328`/`:340` await this success-shaped return. No pending metadata operation is added to the upload retry queue in this path. Server hydration explicitly uses server metadata for existing rows.

Implication: an offline/refused rename, alt-text, tags, site-font flag or folder move can appear applied locally, remain absent remotely, and be overwritten by hydration. Existing server-mirror tests verify successful field mapping, not durable failed-write recovery. Runtime reproduction remains pending; no outage was injected in this worker.

Acceptance for later implementation: failed metadata writes produce truthful pending/error feedback, survive reload if promised, and reconcile on reconnect without losing unrelated metadata or replaying a superseded edit.

### WS-02 — Component retry work does not survive reload (High recovery risk; source-confirmed mechanism, runtime effect pending)

`componentSync.ts:37` creates a SyncRetryQueue; `syncRetryQueue.ts:58` stores tasks as an in-memory Map. Component sync persists server stamps, not a component outbox. Hydration only reads server-listed masters and does not enumerate/replay locally unmirrored masters. By contrast, `cmsSync.ts:99` explicitly adds a persisted outbox to solve the reload-loss problem.

The component failure toast says the change is saved on this device and reconnect replays the queue (`useComponentSync.ts:115`). That claim holds within the same module lifetime. After reload, the queued operation is gone; local master storage can survive, but a failed deletion can rehydrate from the server and a new unsynced master can remain device-only until another edit emits a mirror. Existing component tests exercise reconnect in one module lifetime, not reload recovery. Exit guards may warn; they do not make the queue durable.

Acceptance: explicitly test failed create/update/delete, reload, then reconnect and confirm server/local convergence. Preserve source-specific evidence rather than extrapolating CMS outbox behavior to components.

### WS-03 — Workspace component library read errors become empty results (Medium, source and existing test contract)

`componentSync.ts:216` catches library query failure and returns `[]`. `useComponentList.ts:55` consumes that result with `setLibrary`; its `error` state only covers local getAllComponents. The separate `hydrateComponentsFromServer` toast covers site master hydration, not this library call. Existing componentSync test explicitly expects an empty list on failed library reads.

Implication: the From Library group can appear empty when access/network fails, without a specific retry/error state. Reproduce by failing only `siteComponents.library`, leaving `siteComponents.list` successful; this distinguishes the two requests.

### WS-04 — Analytics check can attribute Buildrick events to an unverified GA ID (Medium, source-confirmed)

`AnalyticsScreen.tsx:verify` sends only siteId to `siteDetail.analyticsStatus`. `server/services/analytics.service.ts:101` counts this site's AnalyticsEvent rows. `ConnectionVerifiedDialog.tsx:45` says the entered measurement ID “is receiving data” whenever that count is positive. A syntactically valid but unrelated GA ID receives the same positive statement. The zero-event title accurately says format only; the positive branch overstates what was checked.

Acceptance: identify these as Buildrick events, or obtain a provider-specific authenticated signal before claiming that a particular GA ID receives data. Do not create fake production events to reproduce this.

### WS-05 — Generic integration secrets lack the Vercel encryption boundary (High security design concern; source-confirmed storage path)

The dashboard's MAILCHIMP form uses `apiKey` (`packages/dashboard/components/settings/integrations-tab.tsx:19`). Generic `addIntegration` and `updateIntegration` pass config directly into Prisma JSON (`server/services/integrations.service.ts:62` and `:107`); no encryption call surrounds that write. ADMIN list reads return full config, and the generic rendered fields use text inputs. Vercel's separate flow explicitly encrypts its token. This differs from the server AGENTS token-at-rest requirement.

No actual secret, stored row or provider account was inspected. This is an application-layer storage/response observation, not a claim that an unauthorized caller can read credentials or that infrastructure encryption is absent. A later security decision should cover write-only credential fields, encryption/migration and redacted return shapes; do not silently migrate during the audit.
