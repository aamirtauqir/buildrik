# Webflow / Framer benchmark and Buildrick gap analysis

10 October 2026. Phase 3 research input. The practical priority is to make Buildrick's existing editing, persistence and release contracts dependable and visible. The evidence does not justify replacing the editor's architecture or adding every competitor capability.

This benchmark uses **30 official primary sources: 16 Webflow and 14 Framer pages**, retrieved on 2026-10-10. The source ledger records titles, URLs, claim scope and limitations in [competitor-sources.json](evidence/competitor-sources.json). Competitor behavior below is **documented, not hands-on verified**: no competitor account was used, no site was published and no message was sent. Search-result article text and direct page opens supplied the evidence. Source publication dates vary; current served documentation takes precedence over remembered or legacy interface descriptions. No performance, visual fidelity, accessibility certification or complete context-menu coverage is inferred.

Buildrick's baseline is [Phase 2 completion](PHASE-2-COMPLETION-REPORT.md), [functional matrix](FUNCTIONAL-AUDIT-MATRIX.md), [81-feature inventory](FEATURE-INVENTORY.md) and the linked domain reports. Gate 2 means the accessible audit is complete; it does not mean every function passes. Existing defects, source-confirmed risks and blocked runtime paths keep their distinct evidence levels.

## How to read the comparison

- **Required correction** means an independently evidenced Buildrick defect or misleading state; competitor documentation supplies context, not proof of that defect.
- **Design principle** means a proposed rule for organizing existing capabilities. Its exact layout still requires the Phase 3 ownership model and later design validation.
- **Preserve** means Buildrick already has useful tested behavior.
- **Optional extension** means a capability documented elsewhere that is not required to repair the audited workflow.
- **Not established** means these sources or the Buildrick audit do not support a stronger claim. It does not mean absent.

The recommendations are audit/design inputs, not implementation authorization. Keep existing document/API contracts and the current Tailwind/Flowbite chrome foundation unless separately approved.

## Priorities for the Buildrick design handoff

These priorities derive from audited user impact. Competitor sources illustrate understandable contracts; they do not determine severity.

| Order | Proposed outcome | Evidence / acceptance boundary | Classification |
|---|---|---|---|
| 1 | Dependable editing transactions and output | CAN-01/02/03 first; CI-01 and UX-09/10/25 next. Geometry remains finite at supported zooms; cancel affects only its own transaction; effective values and same-width output agree. Native gestures and published output still require later verification. | Required corrections, P0/P1; no visual redesign can substitute |
| 2 | Truthful durability, authorization and release readiness | WS-01/02/03, RT-01, RR-01/02/03/04 and WS-04/05. Surface local/server/published status accurately; preserve failed work; authorization binds the actual target; every release entry uses the same readiness contract. | Required corrections; browser-confirmed and source-only findings retain labels |
| 3 | Clear selection and scope throughout the shell | UX-14/18/19/22, CI-01 and panel audit. Page, element(s), breakpoint/state, component definition/instance and token source remain legible when switching owners. Covered chrome must not take focus. | Design principles grounded in existing defects |
| 4 | Consistent action and recovery contracts | MENU-01, PAGE-01, IA-03/04/05/06/07, HIST-01. Menu/palette/shortcut routes share availability and target; explanations survive; comparison includes fields restore changes; Undo promises remain accurate. | Required corrections plus action-ownership design |
| 5 | Preserve useful workspaces and reduce avoidable handoffs | UX-26 and workspace/panel audits. Keep Pages creation intent explicit; retain media chooser versus manager, CMS record scope, master/instance behavior and reliable caller return. Confirm dirty-state and selection behavior before moving surfaces. | Design principles and preservation requirements |
| 6 | Evaluate extensions only after core contracts are dependable | Multiple breakpoint frames, richer variant canvases, advanced timelines, branch review, marketplace distribution and broader AI generation. No audit evidence makes these prerequisites for this redesign. Localization/provider expansion also needs explicit service support. | Optional extensions; not implied approval or missing-module findings |

The design should retain Buildrick's own naming and visual identity. The reusable ideas are scope, hierarchy, state provenance, recoverability and deliberate release actions. Competitor branding, icons, colors, exact layouts and commercial plan structures are not proposed requirements.

## Evidence boundaries carried forward

The benchmark is complete for the requested domains at documentation level. It does not add a competitor hands-on gate or a new user approval flow. It also does not close the existing Buildrick runtime limits.

- **Context-menu precision:** only documented competitor examples were used. Exact menus for every element, submenu placement, disabled reasons, focus loops and viewport collision handling need actual account access before any parity claim.
- **Framer media and variables:** developer references establish operation/data contracts. They do not establish current full media-manager controls or a generic variable system matching Webflow.
- **Responsive and motion:** docs establish authoring concepts, not equivalence of canvas, preview and deployed output. Buildrick's mismatch and unsupported interaction behavior remain findings.
- **Feedback and roles:** no competitor email, invitation, reviewer account, comment delivery or permission matrix was exercised. No assertion of flawless competitor authorization or realtime feedback is made.
- **Scale and accessibility:** no production performance trace, large-site benchmark, contrast review, screen-reader session or supported-browser comparison was run.
- **Figma and implementation:** this artifact proposes no unlabelled functional controls for unsupported Buildrick paths and makes no app, Figma, API, schema or source/test changes.

Use this report with the assessed baseline for the ownership/IA decision, then reconstruct AS-IS states before proposing TO-BE screens. The underlying defects and blocked external tests remain traceable in [TRACKING-MATRIX.csv](TRACKING-MATRIX.csv).
