# Phase 3 — panel and context rules

10 October 2026. This is a **proposed design contract grounded in the current application**, following the [Phase 2 completion report](PHASE-2-COMPLETION-REPORT.md). It does not approve implementation, certify runtime behavior, or create TO-BE Figma screens. AS-IS reconstruction still precedes TO-BE work. “Current” describes inspected source or linked observations; “proposed” describes the recommended rule. All proposed dimensions and responsive transitions require Phase 5 validation.

The [panel audit](PANEL-BEHAVIOR-AUDIT.md) and [context-menu audit](CONTEXT-MENU-AUDIT.md) record the baseline. Where their early “pending” entries were subsequently exercised, use the [extended runtime report](EXTENDED-RUNTIME-AUDIT.md), [Pages/History report](PAGES-HISTORY-AUDIT.md) and domain coverage reports for the later outcome. This specification does not overwrite that evidence.

## 1. Ownership and layout decision

Three approaches were considered:

| Approach | Benefit | Cost / decision |
|---|---|---|
| Retain the current fixed widths and 1366px inspector-overlay breakpoint | Smallest presentation change | Leaves overlay obstruction and unbounded 700px drawer expansion unresolved; insufficient as the final rule |
| Retain existing default widths; determine docking/collapse from the available canvas space | Preserves familiar controls and existing routes; makes responsive behavior explainable | Requires measured content floors and explicit focus/return rules. **Recommended for Phase 5 validation** |
| Make every task a resizable floating panel or full workspace | More space for individual tasks | Introduces new window management, focus and persistence behavior without an assessed need. Not proposed |

The proposal keeps one left discovery/navigation drawer, one right selected-object/task column and the existing dedicated workspaces. Only one right-column owner is visible at a time. A workspace owns its own task and exit; a small property choice remains a popover. No new parallel panel stack, continuous drag-resize system or fourth permanent column is proposed.

Current sources: [shell grid](../../src/editor/rail/LayoutShell.css), [sidebar hosting](../../src/editor/sidebar/LeftSidebar.tsx), [destination configuration](../../src/editor/rail/tabsConfig.ts), [right-column routing](../../src/editor/shell/StudioPanels.tsx), [workspace routing](../../src/editor/sidebar/FullPageRouter.tsx). These are multiple routing/state owners today; consolidating the visible contract must preserve their caller context and site lifecycle, not merely rename tabs. See [R-13](TECHNICAL-DEBT-AND-RISKS.md).

## 2. Dimension profiles and responsive policy

Dimensions below are CSS pixels. Default is the open state; collapsed width zero is a separate state, not a usable minimum. Current tokens are rail **60**, drawer **280**, inspector **300** in [tokens.generated.css](../../src/themes/tokens.generated.css). The existing drawer expansion is **700** in `LeftSidebar.tsx`; it is an expansion toggle, not continuous resizing. No viewport clamp was found on that expansion path. The width-contract test explicitly records that 320 was superseded and is **not** a proven drawer minimum: [tabsConfig.width.test.ts](../../src/editor/rail/__tests__/tabsConfig.width.test.ts).

| Profile | Current evidence | Proposed default / minimum / maximum | Resize, collapse and canvas contract |
|---|---|---|---|
| R — rail | 60 token; viewer modes alter rail visibility | 60 / 60 / 60 when shown | Fixed; existing role/view mode controls visibility. Do not treat hidden rail as a new permission model |
| L — left drawer | 280 default; expansion to 700; no authoritative content minimum | 280 / **280 provisional** / `min(700, available dock budget)` for expanded mode | Fixed default plus existing expand/collapse affordance. Clamp expansion; if minimum does not fit, use the transient mode below. Do not add drag handles to the specification |
| I — Inspector | 300; absolute overlay at viewport ≤1366 | 300 / **300 provisional** / 300 in the first design iteration | Fixed and collapsible. Dock if budget fits; otherwise a clearly temporary overlay. Complex tasks use their existing drill-ins/workspaces, not arbitrary widening |
| T — right task column | Publish, Review, History, Activity, AI and Issues share the inspector region | Same 300 / 300 provisional / 300 profile as I | Replaces I; closing restores the inspector when eligible. A task with unreadable required content is a Phase 5 failed fit, not permission to clip it |
| W — full workspace | Templates, full media, Brand, Settings portal to viewport | Outer default/min/max = viewport width; internal nav starts from existing **256** token | No editor rail/inspector docking inside this host. Internal content is fluid; collapse secondary preview/details before reducing primary form/table usability |
| C — CMS in-place workspace | Replaces canvas + inspector; retains rail and CMS drawer | Outer width = `viewport − rail − open drawer`; minimum is the measured record/table/form requirement, **not established**; maximum is that same available region | Own records/fields content; narrow mode must provide a record/field detail route, not squeeze both. Hint column may collapse before primary content |
| O — transient overlay/dialog | Existing Compare, Preview, dialogs and sheets have different owners | Default from existing surface; minimum intrinsic to actual form; maximum viewport minus existing space-token gutters. No universal new pixel width | Modal surfaces contain focus; nonmodal popovers do not trap focus. Compare/Preview may use the full available viewport; never force all dialogs into 300px |
| M — contextual menu | Canvas menu `minWidth: 200`; current families use different bounds logic | Start from existing 200 minimum; grow to fit labels/shortcuts/reasons, capped at viewport minus `--bk-space-16` on each side | Measure rendered dimensions; flip submenus and clamp to all edges. One inner vertical scroll if necessary; no guessed row-count height |

**Why retain the defaults:** the 280 drawer has a recorded fluid media-grid rationale and a measured 280px Pages runtime; the 300 right column is both a token and measured runtime baseline. Neither proves that every current control fits. Long layer names, accessibility zoom, multi-value fields and disabled reasons must be tested. A proposed minimum must rise or content must reorganize when evidence requires it; it must not be asserted as a browser support guarantee.

**Provisional docking calculation.** Let `W` be viewport width, `R` the visible rail width, `L` the docked left width, `I` the docked right width and `C` the remaining canvas region. Require `C = W − R − L − I ≥ Cfloor`. For initial Phase 5 comparison only, use **Cfloor = 423**, derived from the existing 375px mobile preview frame plus two existing 24px canvas gutters ([PreviewOverlay](../../src/editor/shell/PreviewOverlay.tsx), [canvasStyles](../../src/editor/canvas/canvasStyles.ts)). This is a modest frame-review floor at 100% scale, **not a validated authoring minimum or sufficient desktop-page workspace**. Handles, floating controls and content may demand more room.

With the default widths, both panels consume 640px: 1440 leaves 800, 1280 leaves 640, and 1024 leaves 384. Under this provisional rule, 1024 cannot dock both; retaining the 300px inspector and collapsing the 280px drawer leaves 664. The corresponding provisional threshold is 1063, derived from contents rather than a new arbitrary breakpoint. Do not replace the current 1366 breakpoint until Phase 5 verifies the resulting states. Height matters independently: UX-01 already records clipping at 1280×720.

Proposed response when space runs out:

1. Opening a task retains the current panel if the budget fits. Expansion stops at the computed maximum; disable expansion with a reason if there is no extra room.
2. Preserve the actively used panel; collapse the other docked panel without discarding its selected tab or scroll/search context. At 1024 with Inspector active, the example above collapses the left drawer. An explicit request to open the drawer may temporarily overlay it; it does not silently reduce the page breakpoint or zoom.
3. Show one temporary side overlay at a time. Its close control and Escape restore the prior canvas/panel focus. Clicking outside may dismiss a nonmodal overlay only when this will not discard a draft or interrupt an active gesture. Pointer events must not pass through to select/delete/drag the covered canvas.
4. If one panel plus the rail cannot meet the measured content requirement, provide a viewport-contained task surface with an explicit return. The minimum supported editor viewport remains a validation outcome. Designing mobile **site output** does not establish mobile **editor** support.
5. In full workspaces, preserve primary work first: Brand preview, media details and CMS explanatory hints become explicit secondary views before fields or record actions are clipped. Do not simply hide information with no reachable replacement.

Validate at 1440×900, 1280×720, 1024×768 and 200% browser zoom, with populated content, errors and long names. These are proposed comparison fixtures, not the complete support matrix. No automatic fit/zoom animation may change an active resize/drag coordinate contract (R-01–R-03).

## 3. Per-panel responsibility and behavior

All rows use the dimension profiles above. Every docked panel has a fixed header and a content scroll region; keep action footers visible where they exist. Do not add a second vertical scroller for a section that can share its parent. Trees, tables and preview panes may need separate intentional scroll regions. Horizontal scrolling is appropriate for a genuinely wide data table, not for ordinary form labels and controls.

| Layers / L | Read/select/reorder the document hierarchy, rename layers and act on their structure | Tree owns vertical scroll; reveal selected row without resetting unrelated expansion. ## 4. Shared focus, exit and state contract

These are proposed acceptance rules, not claims that every current surface implements them.

- **One Escape owner:** property popup/menu → dialog/sheet → task/workspace → canvas selection. A key closes only one level. Honor [openEscapeSurface](../../src/shared/utils/openEscapeSurface.ts) and [useColumnPanelEscape](../../src/editor/shell/hooks/useColumnPanelEscape.ts); authored canvas dropdowns must not be mistaken for editor chrome. Typing inputs retain their own cancellation/commit semantics.
- **Return focus deliberately:** keyboard-opened panels focus their heading/search/first meaningful control; pointer canvas selection does not automatically focus Inspector. Closing returns to the opening control when still present, otherwise a stable surface heading/canvas control. A deleted row cannot be the return target.
- **Contain covered workspaces:** modal/fullscreen hosts make covered chrome inert and unavailable to screen readers; do not inert a common ancestor containing the portal itself. Nonmodal docked panels do not trap focus. R-06 / UX-22 remain current defects, not solved by this document.
- **Preserve context:** selection IDs, current page, canvas zoom/scroll, drawer tab/search/expansion and task caller survive a temporary workspace. Explicit page navigation/restore/apply can intentionally change context. A site change must not reuse another site's state or asynchronous result.
- **Keep drafts with their owner:** Settings and record forms use their existing guard/save model; Brand applies immediately. Document undo, local record storage, server sync and deployment are separate boundaries. Never add a generic “Saved” indicator that combines them (R-08).
- **Keep canvas gestures safe:** no panel transition consumes a drag/drop, changes zoom mid-gesture or uses global undo as cancellation. R-01–R-03 and CI-01 remain correctness work even if chrome is improved. Current native drag/reorder has no verified result; proposed layouts require fresh gesture evidence.

## 5. Context actions: scope before presentation

Current [menu registry](../../src/editor/canvas/menus/contextMenuRegistry.ts) groups AI/Duplicate/Delete, Arrange, Style, Structure, Lock/Group/CMS, then Interaction. [Shared element actions](../../src/editor/shared/elementActions.ts) already centralize many handlers. The canvas adapter converts an enabled reason string to a boolean and loses the reason ([standaloneActions.ts](../../src/editor/canvas/menus/actions/standaloneActions.ts), lines 17–30). Some clipboard/structure/selection actions remain separate. Proposed menus, keyboard shortcuts, toolbar overflow, Layers and Inspector must expose the same eligibility and target contract even where their grouping differs.

| Context / action | Current evidence or constraint | Proposed rule |
|---|---|---|
| Right-click outside current selection | Canvas selects the target; clicking a member of multiselection preserves the group | Show target name or count. Freeze target IDs for the open menu; revalidate existence, permissions and lock state when executing |
| Root/document | Root is a structural role, not one more registered type | Show navigation/inspection actions where supported; hide destructive/root-wrap/group actions that cannot apply. Do not advertise a forbidden operation as a normal enabled row |
| Locked target / ancestor lock / read-only role | Current type matrix offers Delete/Cut/Wrap enabled on locked fixtures; this proves misleading eligibility, not successful lock bypass | Preserve inspection and Copy where allowed; disable applicable mutations with a visible reason. Unlock appears only when authorized. Engine write guards remain mandatory; UI filtering cannot replace them |
| Linked component instance | Instance mutation/override rules differ from ordinary nodes | Use existing component restrictions and supported override actions. Explain “edit the component” or the actual restriction; do not silently detach or imply an unimplemented override |
| Copy | Command serializes topmost selected subtrees; canvas menu also attempts OS clipboard write | Copy means selected object(s) and descendants. Show count for multiple roots. OS clipboard denial is recoverable; do not claim paste from arbitrary external HTML is supported |
| Cut / Paste / Delete | Internal command clipboard; per-parent paste offsets and nesting fallback; cut/delete exclude prohibited targets; multi-delete has confirmation flow | Clearly identify targets and affected count, including excluded locked nodes. Validate paste destination/allowed nesting and internal clipboard availability. Preserve the existing confirmation/undo boundary; do not label partial execution as all-selected success |
| Copy parent | No explicit Copy parent menu row exists; tests also assert Select parent absent from this menu | Do not label Copy as copying the parent. Use existing parent selection/navigation then Copy, with the parent visibly selected. A future direct parent-copy door would need explicit parent name, shared command and Phase 5 validation; it is not part of the current capability claim |
| Edit text | Inspector emits `UI_INLINE_EDIT_REQUEST`; actual inline editor checks writable leaf DOM tags and refuses nested editor elements | A proposed menu shortcut may reuse that event only for one eligible rendered text leaf. This is a new entry to an existing action, not a new text engine. Hide for nontext, ambiguous descendants and multi-selection; show lock reason when otherwise eligible |
| Group / Ungroup / Wrap | Canvas Group visible at ≥2 selection; engine additionally requires compatible same-parent elements. Layers can wrap one element. Ungroup currently targets nonempty container | Label **Group selected elements** for multiple compatible siblings; **Wrap in container** for one target. Explain different-parent/locked constraints. Preserve IDs/order and one undo transaction. Do not conflate ungrouping with deleting contained children |
| Arrange | Current actions change sibling order; labels “Bring to front/back” can imply z-index | Name the order being changed and identify parent scope. Enable only where sibling movement is legal and meaningful; first/last positions have reasons. Do not imply these actions write CSS z-index |
| Copy/Paste style | Shared style actions, clipboard state and responsive scope differ from structural clipboard | Separate style clipboard from element clipboard. Show destination count and breakpoint/pseudo-state scope; preserve lock and component guards. Mixed properties do not become invented common values |
| Replace with block | Explicit current type set, not every container; requires caller capability | Preserve exact eligible set below until behavior is deliberately extended. Show lock/availability reason; replacing a child must not unexpectedly replace its ancestor |
| Save as component | Existing creation flow and callback/storage boundary | Open the existing named component flow with selected scope; reflect local/server state. Do not imply a remote library save succeeded from a local master creation |
| Bind to CMS | Capability-filtered for six types | Opens binding for the selected property/object; collection/schema/record management remains CMS. Keep current collection/field validation and caller return |
| Add interaction / animation | Non-root action and existing Inspector behavior; some runtime features unimplemented | Open existing behavior controls. Do not advertise reverse animation as functional while CI-02 persists; do not label script-disabled Preview as a working interaction test |
| AI | Entry depends on callback/availability and scope | Show selected target/count; read-only/restrictions remain explicit. Page/site scope requires the existing deliberate scope choice. Service failure never silently falls back to applying different content |
| Unsupported action | Some product bodies/provider options are deferred or unavailable | Hide structurally irrelevant controls. For a supported action temporarily unavailable, disable with a concrete reason. A planned feature, missing renderer or absent backend is not an enabled placeholder |

For destructive/mutating actions, eligibility is the intersection of **role → project/feature availability → target existence → root/ancestor/component restrictions → type capability → selection compatibility → clipboard/task prerequisites**. Do not automatically apply a single-target submenu to only the first item of a multiselection. If partial execution is the existing supported behavior, state the writable and excluded counts before action; otherwise disable and explain. CI-01 demonstrates why alignment needs the same rule despite being outside the context menu.

Menus use their surface's correct input model: Arrow Up/Down among eligible items, Arrow Right/Left into/out of submenus, Home/End where supported by the shared primitive, Enter/Space activation and Escape returning focus. Retain discoverable disabled reasons for keyboard users. Page shortcuts must target the focused page context, not the canvas. Measure real menu bounds at all four viewport corners with nested submenus and long reasons (R-07 / MENU-01 / PAGE-01); the existing working-tree canvas menu patch is part of the audited baseline, not a change made here.

## 6. Complete 55-type relevance mapping

The following disjoint groups account for **all 55 canonical registered types**. Source of truth is [elementCapabilities.ts](../../src/shared/constants/elementCapabilities.ts), [type-block renderer](../../src/editor/inspector/sections/registry/type.tsx), shared action predicates and the [110-state availability artifact](evidence/context-menu-type-matrix.json). The artifact uses real Composer fixtures with single selection, empty clipboard and an AI callback; it does **not** establish action execution, rendering fidelity or multiselection behavior.

All categories inherit section 5's structural, clipboard, style, lock and permission rules. “Edit leaf” below means the actual rendered leaf tag passes [useCanvasInlineEdit](../../src/editor/canvas/hooks/useCanvasInlineEdit.ts), not simply that its registry name sounds textual. Link capability and CMS binding are separate. Multiselection Inspector should use the existing intersection of applicable capabilities, not a union of irrelevant controls.

| Category (count) and exact types | Current defining Inspector capability | Context relevance / exclusions |
|---|---|---|
| Text (5): `heading`, `text`, `paragraph`, `label`, `link` | Heading/text/label/link blocks; open Typography. Link capability belongs to `link`; CMS binding on all listed except `label` | Edit leaf candidate; CMS for `heading`, `text`, `paragraph`, `link`. No Replace block. Preserve actual tag/child/lock checks |
| Button (1): `button` | Button block, Text inside; Link and CMS capability | Edit leaf candidate for eligible content; Link/CMS doors. No Replace block. Text-inside style is not proof every nested child is inline editable |
| Form controls (7): `input`, `textarea`, `select`, `checkbox`, `radio`, `switch`, `upload` | Input block for input/textarea/select/upload; Choice for checkbox/radio/switch; Text inside | No direct CMS/Link capability and no Replace block. Edit their own supported field properties; an owning form's submission/settings do not become settings on every child |
| Media (6): `image`, `video`, `audio`, `svg`, `icon`, `lottie` | Respective type blocks; svg/icon share SVG block; no Typography | Image alone has CMS binding. Media edit/replace uses the applicable existing type control/chooser, not generic text editing. No Replace block; audio mirroring/provider limits remain visible |
| Embeds (2): `video-embed`, `map-embed` | Respective embed blocks; no Typography | Existing URL/embed controls only; no text/CMS/Replace block door. Do not infer arbitrary executable embed support |
| Utilities (2): `spacer`, `divider` | No defining type block, Layout or Typography capability | General applicable styles/structure only. No empty type section, fake text editor, CMS or Replace block |
| Widgets (3): `countdown`, `progress`, `accordion` | Respective widget blocks; Text inside | Edit supported widget properties/items through their existing controls. No CMS/Replace block. Preview/runtime limitations remain separate from property availability |
| Layout primitives (4): `flex`, `stack`, `grid`, `columns` | Flex block for flex/stack; Grid for grid/columns; Text inside. Generic Layout is false because the type block owns layout | Structure/order actions use actual nesting rules. Replace block applies to `flex`, `grid`, `columns`, **not `stack`** under the current predicate. No CMS |
| General containers (18): `container`, `section`, `card`, `cta`, `hero`, `features`, `header`, `footer`, `nav`, `navbar`, `pricing`, `social`, `testimonials`, `tabs`, `list`, `table`, `gallery`, `custom` | Generic Layout and Text inside; no defining type block. Link capability only for container/section/card/cta | Replace block on container/section/card/cta/hero/features/header/footer/nav/navbar/pricing only. No CMS. Do not infer a specialized tabs/table/gallery editor merely from a generic registry type |
| Structural child (1): `list-item` | Layout/Text inside, structural-child flag; Link/CMS suppressed | Respect owning list's nesting and mutation constraints. No Replace block; no generic parent-destructive shortcut |
| Behavior owners (3): `form`, `slider`, `collection-list` | Generic Layout/Text inside plus form-fields/form-settings, slides/slider-settings, or collection section respectively | Open the existing owner-specific behavior controls; these belong to the owner rather than arbitrary descendants. No direct CMS field-binding or Replace block door; collection configuration is distinct from binding a leaf |
| Reserved product containers (3): `product-card`, `product-grid`, `product-detail` | Generic container capabilities today; product type block is reserved with no body | General layout/style/structure only. No fabricated price, stock, checkout, payment or commerce-management controls; no CMS/Replace block |

Exact current Replace block set is therefore 14 types: `container`, `section`, `hero`, `features`, `header`, `footer`, `nav`, `navbar`, `cta`, `card`, `pricing`, `columns`, `grid`, `flex`. Exact direct CMS set is six: `heading`, `text`, `paragraph`, `link`, `button`, `image`. Unknown legacy types currently fall back to container capabilities; the proposed design must not silently pretend that a missing specialized implementation exists.

Roots, linked component instances, locked ancestors, viewer access and multiselections are **overlays on these types**, not additional registered types. They must be tested independently; 55×2 predicates do not cover them.
